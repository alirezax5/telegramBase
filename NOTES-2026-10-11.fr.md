### 1. Bots gérés (Managed Bots) — de bout en bout, PROUVÉ EN DIRECT
- `request_managed_bot` : le `request_id` DOIT être un **entier**. Une chaîne est rejetée avec
  `Bad Request: Field "request_id" must be a valid Number` (« request_id » doit être un
  nombre valide). L'indication de type `int $requestId` du framework est correcte — ne la
  « corrigez » pas en chaîne.
- Forme réelle de l'update `managed_bot` (update_id 489375148) :
  `{ user: <creator human>, bot: <child bot> }` — l'ENFANT est `bot`, le
  demandeur est `user`. `getManagedBotToken(bot.id)` — passer `user.id` donne
  `Bad Request: user is not a bot` (« l'utilisateur n'est pas un bot »).
- Chaîne complète prouvée : bouton clavier → appui de l'utilisateur → l'update `managed_bot`
  arrive au webhook → `getManagedBotToken` renvoie un token enfant en direct → le `getMe` de
  l'enfant fonctionne → le `sendMessage` de l'enfant est livré à son créateur.
  **Zéro token sur disque.**

### 2. Un seul fichier webhook, plusieurs bots — routage secret_token PROUVÉ (7/7)
- Les deux bots de test (@emojiCustom_bot, @instaroonxbot) ont été armés sur UN seul et même
  fichier (`mb_router.php`) avec des `secret_token` distincts. 7/7 livraisons — `/start`
  réel, deux appuis réels sur des boutons inline par bot, POST synthétiques — la bonne
  identité à chaque fois.
- Telegram ne renvoie en écho QUE le secret que nous définissons dans `setWebhook`, dans
  `X-Telegram-Bot-Api-Secret-Token`. Le token du bot ne voyage jamais dans un en-tête
  (prouvé sur 8/8 variantes d'en-tête) — uniquement dans le chemin d'URL `/bot<token>/`.
- Règles de durcissement : secret aléatoire unique par bot (32+ caractères
  `[A-Za-z0-9_-]`), comparaison avec `hash_equals()`, 403 pour un secret inconnu, ne jamais
  journaliser les tokens, rotation = relancer `setWebhook`.

### 3. Hook guest_message — corrigé dans ce build
- `PluginHandler::UPDATE_TYPES` ne contenait pas `guest_message` (Bot API 10.0) : les
  updates guest synthétiques étaient abandonnés silencieusement. Corrigé : `guest_message`
  ajouté → `onGuestMessage($message, $tg)` se déclenche désormais. Non-régression vérifiée
  contre le dispatch `managed_bot` (aucune casse).

### 4. Correctifs P3.3.1 présents dans ce build (à vérifier lors du pull)
- **F006 ack tardif** — `RabbitQueue::pop()` n'acquitte plus au moment du pop ; le tag de
  livraison est conservé jusqu'à `ack()` après traitement → le broker redélivre en cas de
  mort d'un worker (at-least-once au lieu de at-most-once).
- **Correctif de login AMQPLAIN** — `ConnectionManager::createRabbitMQ()` avait
  `login_method: 'default'` (mécanisme AMQP invalide → boucle de « Broken pipe ») ;
  désormais `AMQPLAIN`.
- **Signaux G10** — `Core::runFetchQueueUpdate()` gère SIGINT/SIGTERM.
- **PollingLoop** — SIGINT/SIGTERM + auto-redémarrage tous les N lots
  (`POLLING_RESTART_INTERVAL`, 0 désactive) pour borner la mémoire.
- **F008** — le point d'entrée webhook rejette les BOT_MODEs réservés au CLI avec un
  HTTP 500 au lieu de bloquer les workers FPM.
- Lacune restante connue : le **driver de file Redis utilise toujours un `LPOP`
  destructif** (perte en cas de crash entre le pop et le traitement). Recommandation :
  Redis Streams — voir `proposal/queue-router-v2/`.

### 5. Architecture de file — recommandation du terrain (important pour les fermes de bots)
- **Webhook XOR polling par bot, jamais les deux** (409 Conflict). Incident réel : un
  daemon de polling oublié a continué de provoquer des 409 contre le webhook armé pendant
  des heures.
- Le point d'entrée webhook ne doit QUE : valider le secret → mettre en file → répondre
  `200` vite (<50 ms). Un webhook à traitement inline de 102 s a été tué par nginx (499)
  en trafic réel — c'est l'anti-pattern que le mode `webhook_queue` de ce build évite.
- Le polling est légitime comme : repli par bot (`ingest_mode=webhook|poll`), schéma de
  fetcher `queue.php` (n'avancer l'offset QU'après une mise en file réussie), ou
  diagnostics temporaires.
- Les ajouts proposés se trouvent dans `proposal/queue-router-v2/` : un routeur de file
  multi-bot autonome + un worker Streams/file, et une esquisse de patch
  d'**autoprotection du PollingLoop** (le poller vérifie `getWebhookInfo` toutes les 60 s
  et se suspend de lui-même lorsqu'un webhook est armé — remède radical aux 409 chroniques).
