# Заметки о выпуске и полевые находки — 2026-10-11

> Русская версия `NOTES-2026-10-11.md` (англ.). Другие языки: `.fa.md`, `.zh.md`, `.fr.md`, `.pt.md`, `.ar.md` (в той же папке).

Полевые находки, проверенные вживую, из тестовой сессии 2026-10-11 (Telegram Bot API
9.6/10.x, реальный трафик, chat 82267967). Каждое приведённое ниже утверждение доказано
на реальном API, а не только по документации.

### 1. Управляемые боты (Managed Bots) — сквозной сценарий ПОЛНОСТЬЮ ДОКАЗАН ВЖИВУЮ
- В `request_managed_bot` поле `request_id` ОБЯЗАТЕЛЬНО должно быть **целым числом**.
  Строка отклоняется с ошибкой `Bad Request: Field "request_id" must be a valid Number`
  («поле "request_id" должно быть числом»). Объявление типа `int $requestId` во
  фреймворке корректно — не «исправляйте» его на строку.
- Реальная структура обновления `managed_bot` (update_id 489375148):
  `{ user: <creator human>, bot: <child bot> }` — ДОЧЕРНИЙ бот — это `bot`, запросивший —
  `user`. `getManagedBotToken(bot.id)` — передача `user.id` даёт
  `Bad Request: user is not a bot` («user — не бот»).
- Полная цепочка доказана: кнопка клавиатуры → пользователь нажимает → обновление
  `managed_bot` приходит на вебхук → `getManagedBotToken` возвращает живой токен
  дочернего бота → дочерний `getMe` работает → дочерний `sendMessage` доставлен его
  создателю. **Ноль токенов на диске.**

### 2. Один файл вебхука, много ботов — маршрутизация по secret_token ДОКАЗАНА (7/7)
- Оба тестовых бота (@emojiCustom_bot, @instaroonxbot) были настроены на ОДИН файл
  (`mb_router.php`) с разными `secret_token`. 7/7 доставок — реальный `/start`,
  по два реальных нажатия инлайн-кнопки от каждого бота, синтетические POST —
  правильная идентичность каждый раз.
- Telegram возвращает в `X-Telegram-Bot-Api-Secret-Token` ТОЛЬКО тот секрет, который мы
  задали в `setWebhook`. Токен бота никогда не передаётся ни в одном заголовке
  (доказано на 8/8 вариантах заголовков) — только в пути URL `/bot<token>/`.
- Правила ужесточения: уникальный случайный секрет на каждого бота (32+ символов
  `[A-Za-z0-9_-]`), сравнение через `hash_equals()`, 403 на неизвестный секрет, никогда
  не логировать токены, ротация = повторно выполнить `setWebhook`.

### 3. Хук guest_message — пропатчен в этой сборке
- В `PluginHandler::UPDATE_TYPES` отсутствовал `guest_message` (Bot API 10.0):
  синтетические гостевые обновления молча отбрасывались. Пропатчено: `guest_message`
  добавлен → теперь срабатывает `onGuestMessage($message, $tg)`. Проверено на регрессию
  против диспетчеризации `managed_bot` (ничего не сломалось).

### 4. Фиксы P3.3.1 присутствуют в этой сборке (проверьте после pull)
- **F006 ack-late** — `RabbitQueue::pop()` больше не подтверждает (ack) сообщение при
  извлечении; delivery tag удерживается до `ack()` после обработки → при гибели воркера
  брокер доставит повторно (at-least-once вместо at-most-once).
- **Фикс входа AMQPLAIN** — в `ConnectionManager::createRabbitMQ()` стоял
  `login_method: 'default'` (невалидный механизм AMQP → цикл «Broken pipe»
  («сломанный канал»)); теперь `AMQPLAIN`.
- **Сигналы G10** — `Core::runFetchQueueUpdate()` обрабатывает SIGINT/SIGTERM.
- **PollingLoop** — SIGINT/SIGTERM + самоперезапуск каждые N батчей
  (`POLLING_RESTART_INTERVAL`, 0 отключает), чтобы ограничивать потребление памяти.
- **F008** — входная точка вебхука отклоняет режимы BOT_MODE, работающие только через
  CLI, ответом HTTP 500 вместо зависания воркеров FPM.
- Известный оставшийся пробел: **драйвер очереди Redis по-прежнему использует
  деструктивный `LPOP`** (потеря при падении между pop и обработкой).
  Рекомендация: Redis Streams — см. `proposal/queue-router-v2/`.

### 5. Архитектура очередей — полевая рекомендация (важно для ферм ботов)
- **На каждого бота — вебхук XOR опрос (polling), никогда оба сразу** (409 Conflict).
  Реальный инцидент: забытый демон опроса часами продолжал получать 409 против
  активного вебхука.
- Вебхук-эндпоинт должен ТОЛЬКО: проверить секрет → поставить в очередь → быстро
  ответить `200` (<50 мс). Вебхук со встроенной обработкой, работавший 102 с, был убит
  nginx (499) в живом трафике — именно этого антипаттерна избегает режим `webhook_queue`
  этой сборки.
- Опрос легитимен как: резерв на каждого бота (`ingest_mode=webhook|poll`), паттерн
  фетчера `queue.php` (продвигать смещение (offset) ТОЛЬКО после успешной постановки в
  очередь) или временная диагностика.
- Предлагаемые дополнения лежат в `proposal/queue-router-v2/`: автономный
  мульти-бот-роутер очередей + воркер Streams/файлов, а также набросок патча
  **самоконтроля PollingLoop** (поллер каждые 60 с проверяет `getWebhookInfo` и
  самоприостанавливается, когда вебхук активен — радикальное средство от хронических
  409).
