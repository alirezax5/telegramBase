### 1. Bots gerenciados — ponta a ponta completa COMPROVADA AO VIVO
- `request_managed_bot`: `request_id` DEVE ser um **inteiro**. Uma string é rejeitada com
  `Bad Request: Field "request_id" must be a valid Number` (PT: "request_id deve ser um número
  válido"). A dica de tipo `int $requestId` do framework está correta — não a "corrija" para string.
- Formato real do update `managed_bot` (update_id 489375148):
  `{ user: <creator human>, bot: <child bot> }` — o FILHO é `bot`, quem solicitou é `user`.
  `getManagedBotToken(bot.id)` — passar `user.id` retorna
  `Bad Request: user is not a bot` (PT: "usuário não é um bot").
- Cadeia completa comprovada: botão de teclado → usuário toca → o update `managed_bot` chega ao
  webhook → `getManagedBotToken` retorna um token de bot filho ao vivo → o `getMe` do filho
  funciona → o `sendMessage` do filho é entregue ao seu criador. **Zero tokens em disco.**

### 2. Um arquivo de webhook, vários bots — roteamento por secret_token COMPROVADO (7/7)
- Os dois bots de teste (@emojiCustom_bot, @instaroonxbot) foram armados em UM único arquivo
  (`mb_router.php`) com `secret_token`s distintos. 7/7 entregas — `/start` real, dois toques reais
  em botões inline por bot, POSTs sintéticos — identidade correta a cada vez.
- O Telegram devolve APENAS o segredo que definimos no `setWebhook`, no cabeçalho
  `X-Telegram-Bot-Api-Secret-Token`. O token do bot nunca viaja em nenhum cabeçalho (comprovado
  em 8/8 variantes de cabeçalho) — apenas no caminho da URL `/bot<token>/`.
- Regras de hardening: segredo aleatório único por bot (32+ caracteres `[A-Za-z0-9_-]`),
  comparação com `hash_equals()`, 403 para segredo desconhecido, nunca registrar tokens em logs,
  rotação = executar `setWebhook` novamente.

### 3. Hook guest_message — patch aplicado neste build
- `PluginHandler::UPDATE_TYPES` não tinha `guest_message` (Bot API 10.0): updates sintéticos de
  guest eram descartados em silêncio. Corrigido: `guest_message` adicionado →
  `onGuestMessage($message, $tg)` agora dispara. Checagem de regressão feita contra o despacho de
  `managed_bot` (sem quebras).

### 4. Correções da P3.3.1 presentes neste build (verifique ao fazer pull)
- **F006 ack tardio (ack-late)** — `RabbitQueue::pop()` não faz mais ack no pop; a tag de entrega
  é mantida até o `ack()` após o processamento → o broker reentrega em caso de morte do worker
  (at-least-once — pelo menos uma vez — em vez de at-most-once — no máximo uma vez).
- **Correção de login AMQPLAIN** — `ConnectionManager::createRabbitMQ()` tinha
  `login_method: 'default'` (mecanismo AMQP inválido → loop de "Broken pipe" / pipe quebrado);
  agora `AMQPLAIN`.
- **Sinais G10** — `Core::runFetchQueueUpdate()` trata SIGINT/SIGTERM.
- **PollingLoop** — SIGINT/SIGTERM + reinício automático a cada N lotes
  (`POLLING_RESTART_INTERVAL`, 0 desativa) para limitar o uso de memória.
- **F008** — a entrada do webhook rejeita BOT_MODEs exclusivos de CLI com HTTP 500, em vez de
  deixar workers do FPM travados.
- Lacuna remanescente conhecida: o **driver de fila do Redis ainda usa `LPOP` destrutivo**
  (perda em caso de crash entre o pop e o processamento). Recomendação: Redis Streams —
  veja `proposal/queue-router-v2/`.

### 5. Arquitetura de filas — recomendação de campo (importante para fazendas)
- **Webhook XOR polling por bot, nunca ambos** (409 Conflict). Incidente real: um daemon de
  polling remanescente passou horas gerando 409 contra o webhook armado.
- O endpoint de webhook deve APENAS: validar o segredo → enfileirar → responder `200` rápido
  (<50 ms). Um webhook com processamento inline de 102 s foi morto pelo nginx (499) em tráfego
  real — esse é o antipadrão que o modo `webhook_queue` deste build evita.
- O polling é legítimo como: fallback por bot (`ingest_mode=webhook|poll`), o padrão de fetcher
  do `queue.php` (avançar o offset SOMENTE após o enfileiramento bem-sucedido) ou diagnósticos
  temporários.
- As adições propostas ficam em `proposal/queue-router-v2/`: um roteador de fila multi-bot
  independente + worker de Streams/arquivo, e um esboço de patch de **autoguarda do PollingLoop**
  (o poller consulta `getWebhookInfo` a cada 60 s e se auto-suspende quando há um webhook armado —
  cura radical para os 409 crônicos).
