# Release Notes & Field Findings — 2026-10-11

Live-verified findings from the 2026-10-11 test session (Telegram Bot API 9.6/10.x,
real traffic, chat 82267967). Every claim below was proven against the real API,
not just docs. Translations: `NOTES-2026-10-11.fa.md`, `.zh.md`, `.ru.md`, `.fr.md`, `.pt.md`, `.ar.md` (same folder).

### 1. Managed Bots — full end-to-end PROVEN LIVE
- `request_managed_bot`: `request_id` MUST be an **integer**. A string is rejected
  with `Bad Request: Field "request_id" must be a valid Number`. The framework's
  `int $requestId` hint is correct — do not "fix" it to string.
- Real `managed_bot` update shape (update_id 489375148):
  `{ user: <creator human>, bot: <child bot> }` — the CHILD is `bot`, the
  requester is `user`. `getManagedBotToken(bot.id)` — passing `user.id` gives
  `Bad Request: user is not a bot`.
- Full chain proven: keyboard button → user taps → `managed_bot` update arrives at
  the webhook → `getManagedBotToken` returns a live child token → child `getMe`
  works → child `sendMessage` delivered to its creator. **Zero tokens on disk.**

### 2. One webhook file, many bots — secret_token routing PROVEN (7/7)
- Both test bots (@emojiCustom_bot, @instaroonxbot) were armed to ONE file
  (`mb_router.php`) with distinct `secret_token`s. 7/7 deliveries — real `/start`,
  two real inline-button taps per bot, synthetic POSTs — correct identity every time.
- Telegram echoes ONLY the secret we set in `setWebhook` in
  `X-Telegram-Bot-Api-Secret-Token`. The bot token never travels in any header
  (proven 8/8 header variants) — only in the URL path `/bot<token>/`.
- Hardening rules: unique random secret per bot (32+ chars `[A-Za-z0-9_-]`),
  compare with `hash_equals()`, 403 on unknown secret, never log tokens,
  rotation = re-run `setWebhook`.

### 3. guest_message hook — patched in this build
- `PluginHandler::UPDATE_TYPES` lacked `guest_message` (Bot API 10.0): synthetic
  guest updates were silently dropped. Patched: `guest_message` added →
  `onGuestMessage($message, $tg)` now fires. Regression-checked against
  `managed_bot` dispatch (no breakage).

### 4. P3.3.1 fixes present in this build (verify on pull)
- **F006 ack-late** — `RabbitQueue::pop()` no longer acks on pop; delivery tag is
  held until `ack()` after processing → broker redelivers on worker death
  (at-least-once instead of at-most-once).
- **AMQPLAIN login fix** — `ConnectionManager::createRabbitMQ()` had
  `login_method: 'default'` (invalid AMQP mechanism → "Broken pipe" loop);
  now `AMQPLAIN`.
- **G10 signals** — `Core::runFetchQueueUpdate()` handles SIGINT/SIGTERM.
- **PollingLoop** — SIGINT/SIGTERM + self-restart every N batches
  (`POLLING_RESTART_INTERVAL`, 0 disables) to bound memory.
- **F008** — webhook entry rejects CLI-only BOT_MODEs with HTTP 500 instead of
  hanging FPM workers.
- Known remaining gap: the **Redis queue driver still uses destructive `LPOP`**
  (loss on crash between pop and process). Recommendation: Redis Streams —
  see `proposal/queue-router-v2/`.

### 5. Queue architecture — field recommendation (important for farms)
- **Webhook XOR polling per bot, never both** (409 Conflict). A real incident:
  a leftover polling daemon kept 409-ing against the armed webhook for hours.
- Webhook endpoint must ONLY: validate secret → enqueue → respond `200` fast
  (<50 ms). A 102 s inline-processing webhook was killed by nginx (499) in live
  traffic — that is the anti-pattern this build's `webhook_queue` mode avoids.
- Polling is legitimate as: per-bot fallback (`ingest_mode=webhook|poll`), the
  `queue.php` fetcher pattern (advance offset ONLY after successful enqueue), or
  temporary diagnostics.
- Proposed additions live in `proposal/queue-router-v2/`:
  a standalone multi-bot queue router + Streams/file worker, and a
  **PollingLoop self-guard** patch sketch (poller checks `getWebhookInfo` every
  60 s and self-suspends when a webhook is armed — root cure for chronic 409s).
