# Поиск неисправностей — симптомы, причины, решения

## Загрузка и конфигурация

| Симптом | Вероятная причина | Решение |
|---------|-------------------|---------|
| `BOT_TOKEN is not set or empty` на `migrate:status` | старое поведение | исправлено в текущей версии — команды миграции больше не требуют токена. Если вы всё ещё это видите, запустите с `TGBASE_SKIP_BOT_VALIDATION=1` |
| `could not find driver` на `migrate` | `DATABASE_ENABLE=true`, но не настроен PDO-драйвер/БД | установите `DATABASE_ENABLE=false`, если БД не нужна, или установите PDO-драйвер |
| Загрузка падает с ошибкой валидации, связанной с режимом | `BOT_MODE` с опечаткой | используйте ровно одно из: `update_direct`, `update_queue`, `webhook_direct`, `webhook_queue`, `cronjob_update`, `cronjob_queue` |
| Логи появляются в CWD вместо `logs/` | старое поведение — относительный путь логов разрешался относительно CWD | исправлено: `LogHandler` использует `LoggerConfig::absolutePath()` (относительно базовой папки проекта). Также это затрагивало запуск `bin/tgbase` из другого каталога |
| `Session::regenerate()` фатален: «Cannot modify readonly property» | старое поведение | исправлено: `Session` больше не объявляет `$sessionId` readonly |
| `tests/smoke.php` проваливает все негативные случаи | старая сломанная логика match | исправлено в текущей версии |
| Плагины не загружаются | неверный `PLUGINS_DIR` или устаревший кэш плагинов | по умолчанию `/Plugin/` (относительно базовой папки проекта; поддерживаются абсолютные пути). Для разработки установите `PLUGIN_CACHE_ENABLED=false`, затем `php bin/tgbase plugins` для проверки обнаружения |
| Падение лимитера/админ-гварда на callback queries | старый не-nullsafe доступ `->message->chat->id` | исправлено: nullsafe-цепочки + поддержка `edited_message` / `channel_post` / `chat_member` |

## Вебхук

| Симптом | Вероятная причина | Решение |
|---------|-------------------|---------|
| Вебхук возвращает `403` на каждую доставку | активен белый список IP, но прокси/CDN переписывает IP источника | за Cloudflare/nginx установите `WEBHOOK_CHECK_IP=false` и полагайтесь на сильный `BOT_WEBHOOK_SECRET` — см. [webhook.md](webhook.md) |
| Вебхук возвращает `403`, `getWebhookInfo` сообщает о несовпадении секрета | `BOT_WEBHOOK_SECRET` в `.env` ≠ `secret_token`, переданный в `setWebhook` | сделайте их идентичными; меняйте через `openssl rand -hex 32` |
| Вебхук возвращает `500` с «BOT_MODE ... is CLI-only» | CLI-only режим на веб-точке входа (SAPI-защита v2.4.0) | установите `BOT_MODE=webhook_direct` / `webhook_queue` для веб-точки входа или запускайте режим из CLI (`bot.php` / `queue.php`) |
| `getWebhookInfo`: `last_error_message="Read timeout expired"` | конечная точка не ответила вовремя (до v2.4.0 это мог быть баг бесконечного цикла; после v2.4.0 — медленные хендлеры) | обновитесь до ≥ v2.4.0; проверьте на медленные хендлеры; вынесите тяжёлую работу в `webhook_queue` |
| `pending_update_count` продолжает расти | ваша конечная точка постоянно недоступна/сбоит | проверьте `last_error_message`, валидность TLS-сертификата и что `webhook.php` доступен; голый GET, возвращающий `400 empty`, доказывает, что диспетчер жив |
| Ответы вебхука запаздывают на секунды | хендлеры выполняются инлайн во время HTTP-запроса | переключитесь на `webhook_queue` — тогда конечная точка отвечает немедленно, а воркеры обрабатывают асинхронно |

## Очереди и воркеры

| Симптом | Вероятная причина | Решение |
|---------|-------------------|---------|
| `RabbitMQ ... "Broken pipe or closed connection"` при подключении | старый баг метода логина (`default` — не валидный AMQP-механизм) | исправлено в v2.4.0 (драйвер теперь использует `AMQPLAIN`); в любом случае проверьте своего пользователя/vhost RabbitMQ |
| Обновления отправляются, но никогда не обрабатываются | консюмер не запущен | режимам `*_queue` нужны обе стороны: продюсер (`queue.php` или `webhook.php`) **и** консюмер (`php bot.php`) |
| Очередь растёт безгранично, пока воркеры лежат | | установите `QUEUE_MAX_SIZE` (ограниченные очереди при заполнении отклоняют + логируют) |
| Повторная обработка после падения воркера | ожидаемо при at-least-once (ack-late RabbitMQ, повторная доставка webhook/polling) | сделайте хендлеры идемпотентными — см. [reliability.md](reliability.md) |
| Воркер молча завершается под нагрузкой | отсутствует супервизор | запускайте все долгие процессы под systemd/supervisord с `Restart=always`; фреймворк сам перезапускает polling каждые `POLLING_RESTART_INTERVAL` батчей, супервизор покрывает всё остальное |
| `409 Conflict` от `getUpdates` | два процесса опрашивают один токен бота (или вебхук + polling одновременно) | только один источник обновлений: запустите единственный фетчер и выполните `deleteWebhook` перед запуском polling |

## Заметки по развёртыванию, стоящие своего веса

- **Права на файл логов (FPM):** если webhook-точка входа не может писать логи, обычно дело в владельце файла — PHP-FPM работает как `www-data`/`www`, поэтому файлы/каталоги логов должны быть доступны для записи этому пользователю (`chown www-data:www-data logs -R`). Молчаливый no-op при записи лога иначе трудно заметить.
- **PHP-FPM `request_terminate_timeout`:** всё, что ваш webhook-хендлер делает дольше этого лимита, умирает с 502. Держите обработку вебхука быстрой; остальное — в очередь.
- **`php bin/tgbase doctor`** — самый быстрый инструмент триажа: он проверяет версию/расширения PHP, читаемость `.env`, доступность `AppData/` для записи, записываемость логов и формат токена, не касаясь Telegram.
- **Два источника обновлений воюют:** после переключения между polling и вебхуком убедитесь, что переключение завершено (`deleteWebhook` или чистая остановка polling) перед запуском другой стороны. Оба сразу = конфликты смещений и 409-е.

## Быстрая справка по диагностике

```bash
php bin/tgbase doctor              # environment triage
php bin/tgbase plugins             # what the framework actually discovered
php tests/smoke.php                # 6-case bootstrap check
php tests/run.php --filter=Queue   # subsystem deep-dive
curl "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"   # Telegram-side view
```
