# Режимы бота — шесть способов запустить TelegramBase-бота

`BOT_MODE` в `.env` — самое важное конфигурационное значение. Оно решает, *как обновления поступают* (polling или вебхук) и *как они обрабатываются* (инлайн или через очередь).

## Режимы

| Режим | Источник обновлений | Обработка | Процессы, которые вы запускаете |
|-------|---------------------|-----------|---------------------------------|
| `update_direct` *(по умолчанию)* | long-poll `getUpdates` | инлайн, тот же процесс | `php bot.php` под супервизором |
| `update_queue` | long-poll `getUpdates` | асинхронно через очередь | `php queue.php` (фетчер) + один или несколько `php bot.php` (воркеры) |
| `webhook_direct` | POST вебхука Telegram | инлайн, внутри HTTP-запроса | только веб-сервер (`webhook.php`) |
| `webhook_queue` | POST вебхука Telegram | асинхронно через очередь | веб-сервер (`webhook.php`) + воркер(ы) `php bot.php` |
| `cronjob_update` | `getUpdates` (polling) | инлайн, **самозалечивающийся демон** — первый тик запускает бесконечный цикл, последующие тики ничего не делают, пока он жив | crontab `* * * * * php bin/scheduler.php` |
| `cronjob_queue` | только очередь (без polling Telegram) | асинхронный батч — каждый тик потребляет до `CRON_MAX_TIME` (по умолчанию 50 с), затем выходит | crontab + слоты `CRON_WORKER` |

Ментальная модель:

- Режимы **`update_*` / `cronjob_*`** сами забирают обновления (ваш сервер обращается к Telegram).
- Режимы **`webhook_*`** принимают обновления (Telegram обращается к вашему серверу).
- **`*_direct`** обрабатывает обновление прямо там, где оно поступило — проще всего, и для большинства ботов этого достаточно.
- **`*_queue`** отделяет приём от обработки — используйте, когда хендлеры медленные (загрузки файлов, внешние API) или когда нужно горизонтальное масштабирование.
- Режимы **`cronjob_*`** запускаются из обычного crontab — супервизор, systemd и Docker не требуются.

## Cron-режимы подробно

Оба cron-режима используют один и тот же механизм безопасности: на каждом тике фреймворк пытается захватить **слот воркера** — эксклюзивный `flock()` на файле блокировки в `data/cron-slots/` (`WorkerLocker`). Если все слоты `CRON_WORKER` заняты, тик логирует `All N worker slots busy` и завершается за миллисекунды — параллельные тики никогда не обработают что-либо дважды.

### `cronjob_update` — самозалечивающийся демон, а не батч

Несмотря на название, тик **не** выполняет «один батч». Первый тик захватывает слот и запускает тот же бесконечный polling-цикл, что и `update_direct` (`set_time_limit(0)` + long-poll), и этот тик никогда не завершается — так задумано:

1. Тик 1 → демон запускается, слот остаётся заблокированным.
2. Тики 2..N → видят занятый слот, завершаются за миллисекунды (замерено: ~30–45 мс). Это *нормально*, а не ошибка.
3. Демон умирает (падение, OOM, перезагрузка) → следующий cron-тик автоматически запускает новый демон. **Cron выступает супервизором.**

Проверено вживую: демон, запущенный в 09:24:01, обработал реальное сообщение инлайн, пережил несколько минутных границ, корректно завершился по SIGTERM в пределах одного long-poll-цикла (~12 с — сигнал остановки учитывается сразу после возврата текущего long-poll), освободил блокировку, и самый следующий тик перезапустил его.

### `cronjob_queue` — ограниченный по времени батч-воркер

Каждый тик захватывает слот и потребляет из очереди не более `CRON_MAX_TIME` секунд (по умолчанию 50), затем аккуратно завершается с `Limited worker finished: N updates`. В этом режиме Telegram никто не опрашивает — очередь должна пополняться продюсером (`webhook_queue` либо ваш собственный запуск `queue.php`).

Проверено вживую: реальное сообщение, отправленное в RabbitMQ в 09:22:49, было извлечено и диспетчеризовано тиком, который уже находился внутри своего 50-секундного окна (`onMessage` плагина в 09:22:49.6, `Limited worker finished: 1 updates` в 09:22:51), а очередь опустошилась обратно до 0/0. Семантика доставки наследуется от драйвера очереди — at-least-once с RabbitMQ начиная с v2.4.0.

### Конфигурация cron

| Env | По умолчанию | Значение |
|-----|--------------|----------|
| `CRON_WORKER` | `1` | число параллельных слотов воркера (flock-файлы в `data/cron-slots/`) |
| `CRON_MAX_TIME` | `50` | окно батча `cronjob_queue` в секундах — держите его ниже интервала cron, чтобы тики не перекрывались |

## Точки входа и SAPI-защита

| Файл | Запускается как | Назначение |
|------|-----------------|------------|
| `bot.php` | CLI | polling (`update_direct`), консюмер очереди (`*_queue`), cron-обратные вызовы |
| `queue.php` | CLI | *продюсер* очереди — делает long-poll Telegram и отправляет обновления в очередь (`update_queue`) |
| `webhook.php` | HTTP | принимает POST вебхуков Telegram (`webhook_*`) |
| `bin/tgbase` | CLI | диагностика, скаффолдинг, миграции |
| `bin/scheduler.php` | CLI | исполнитель cron-тиков (`cronjob_*` + запланированные задачи) |

**Важно — SAPI-защита (v2.4.0):** HTTP-запрос может обслуживать только работу в стиле вебхука. Если `webhook.php` выполняется, когда `BOT_MODE` — режим только для CLI, фреймворк отказывается запускать бесконечный цикл внутри вашего веб-воркера:

| `BOT_MODE` на `webhook.php` | Поведение |
|------------------------------|-----------|
| `webhook_direct` | валидация → обработка инлайн → `200` |
| `webhook_queue` | валидация → постановка в очередь → `200` |
| `update_direct` | валидация → обработка инлайн → `200` (логируется предупреждение — вы, скорее всего, имели в виду `webhook_direct`) |
| `update_queue`, `cronjob_*` | **HTTP 500** с пояснительным сообщением — никакого цикла, никакого зависания |

Предыстория: до появления этой защиты вебхук, направленный на бота, настроенного на `update_direct`, молча запускал бесконечный цикл `getUpdates` внутри PHP-FPM-воркера. Telegram никогда не получал ответ (`Read timeout expired` → бесконечные повторные попытки), а FPM убивал воркер по `request_terminate_timeout` (502). Защита превращает это молчаливое зависание в громкий и быстрый отказ. Логику обнаружения можно проверить напрямую через `Core::isHttpSapi($sapi)`.

> Правило большого пальца: **CLI-режимы запускаются из терминала, webhook-режимы — из веба.** Фреймворк принудительно поддерживает эту границу за вас.

## Семантика доставки кратко

| Путь | Гарантия | Окно дубликатов |
|------|----------|-----------------|
| `webhook_direct` | at-least-once (Telegram повторяет, пока не получит 2xx) | падение *после* `handle()`, но до 200 |
| `update_direct` | at-least-once (смещение продвигается только после обработки) | падение *после* побочных эффектов, но до записи смещения |
| `webhook_queue` (сторона продюсера) | обновление в брокере, как только вы получили свой 200 | повторные попытки постановки в очередь при сбое брокера |
| консюмер очереди — **RabbitMQ** | at-least-once (ack после обработки, v2.4.0) | падение между обработкой и ack |
| консюмер очереди — Redis / JSON / Memcached | at-most-once (разрушающий pop — задача исчезает в момент pop) | падение посреди обработки теряет задачу |

Полные доказательства crash-тестов и руководство по идемпотентности: [reliability.md](reliability.md).

`cronjob_update` ведёт себя в точности как `update_direct` (одно сообщение обрабатывается инлайн до продвижения смещения); `cronjob_queue` ведёт себя в точности как консюмер очереди своего драйвера (at-least-once с RabbitMQ, at-most-once с Redis/JSON/Memcached).

## Выбор режима — практические советы

- **Маленькие боты, дашборды, прототипы** → `update_direct`. Один процесс, нулевая инфраструктура.
- **Медленные хендлеры (обработка файлов, сторонние API), несколько инстансов** → `webhook_queue` или `update_queue` с Redis/RabbitMQ.
- **Общий хостинг без CLI-демонов** → `cronjob_update` (crontab становится супервизором) или `webhook_direct`.
- **Нужен exactly-once?** Ни у кого его нет. TelegramBase даёт пути *at-least-once*, которые никогда не теряют обновления, и пути *at-most-once*, которые никогда не дублируют — выбирайте под конкретный сценарий и делайте хендлеры идемпотентными (см. [reliability.md](reliability.md)).
