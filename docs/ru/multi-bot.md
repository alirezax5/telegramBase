# Мульти-бот — запуск двух ботов в одном процессе

TelegramBase поддерживает мульти-бот-работу на двух уровнях: базовая
[библиотека `telegramBotPhp`](https://github.com/alirezax5/telegramBotPhp) предоставляет
примитивы (независимые экземпляры, стек токенов, сырые вызовы), а фреймворк добавляет
реестр **`BotManager`**, чтобы плагины могли обращаться к вторичным ботам по имени.

Оба запрошенных владельцем сценария были проверены вживую (2026-10-11) на двух реальных ботах:

| Сценарий | Что происходит | Проверенный результат |
|---|---|---|
| **A — проверка членства через бота #2** | пользователь спрашивает бота #1; бот #1 выполняет `getChatMember()` **с токеном бота #2** | `ok=true`, `status=member`, 13 мс |
| **B — делегированная отправка** | пользователь спрашивает бота #1; бот #1 заставляет **бота #2 отправить** сообщение внутри процесса бота #1 | доставлено, 239 мс |

---

## Регистрация дополнительных ботов: `BOT_EXTRA_BOTS`

Добавьте переменную окружения до загрузки (в `.env` или окружении процесса):

```dotenv
BOT_EXTRA_BOTS="second:398172019:AAxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

Правила формата:

- записи **разделяются запятыми**; каждая запись — `name:token`;
- разбиение выполняется только по **первому** двоеточию (сам токен бота содержит двоеточие);
- имя `main` зарезервировано за основным ботом и в этом списке игнорируется;
- некорректные записи логируются (warning) и пропускаются — загрузка никогда не падает.

`BotManager` — синглтон, создаваемый при первом использовании; бот по умолчанию (`main`)
строится из `Config::bot()` (то есть `BOT_TOKEN`), затем регистрируются дополнительные.

## Использование ботов из плагина

```php
use alirezax5\TelegramBase\App\Bot\BotManager;
use alirezax5\TelegramBase\App\Plugin\Contract\PluginInterface;
use telegramBotApiPhp\Telegram;

class MultiBotPlugin implements PluginInterface
{
    public function getPriority(): int { return 1; }

    public function onMessage($message, Telegram $tg): void
    {
        if ($message->text !== '/inchannel') {
            return;
        }

        $bm  = BotManager::getInstance();
        $userId = $tg->fromId();
        $chatId = $tg->chatId();

        // Scenario A — membership check executed by bot #2's identity
        if ($bm->has('second')) {
            $member = $bm->get('second')->getChatMember('@mychannel', $userId);
            $status = $member->result->status ?? 'left';   // member|administrator|creator|left|kicked
            $tg->sendMessage($chatId, "وضعیت عضویت شما (چک توسط ربات ۲): {$status}");
        } else {
            $tg->sendMessage($chatId, 'ربات دوم ثبت نشده — BOT_EXTRA_BOTS را تنظیم کنید');
        }

        // Scenario B — bot #1 sends AS bot #2 (token stack on the main instance)
        if ($bm->has('second')) {
            $tg->switchToken($bm->get('second')->getToken());
            try {
                $tg->sendMessage($chatId, 'این پیام با هویت ربات ۲ ارسال شد (داخل پروسه ربات ۱)');
            } finally {
                $tg->restoreToken();
            }
        }
    }
}
```

## API `BotManager`

| Метод | Поведение |
|---|---|
| `getInstance(): BotManager` | доступ к синглтону |
| `get(?string $name): Telegram` | возвращает именованного бота; **неизвестные имена откатываются к `main`** (логируется предупреждение) |
| `has(string $name): bool` | зарегистрировано ли имя? — **всегда проверяйте перед `get()` не-дефолтного бота** |
| `add(string $name, Telegram $bot): void` | регистрирует/перезаписывает бота во время выполнения (перезапись логируется предупреждением) |
| `names(): string[]` | все зарегистрированные имена (`main` первым) |
| `setDefaultToken(string $token): Telegram` | глобально переопределяет токен **главного** бота — влияет на всех вызывающих |

## Почему важен `has()`

`get('typo-name')` не выбрасывает исключение — он молча возвращает **главного** бота.
Тогда `getChatMember()`, предназначенный для бота #2, будет выполнен от личности бота #1 и
вернёт `chat member not found` или того хуже — неверный, но правдоподобный ответ. Оградите
каждое обращение к не-дефолтному боту через `has()`.

## Управление токенами: несколько ботов в одном файле

Один деплой (один входной файл + один `.env`) может обслуживать любое количество
ботов-личностей. Поддерживаются три стратегии — в порядке рекомендации:

| # | Стратегия | Где живут токены | Лучше всего подходит для | Проверено |
|---|---|---|---|---|
| 1 | **Статический реестр** — `BOT_TOKEN` + `BOT_EXTRA_BOTS` в `.env` | один `.env`, пары `name:token` | фиксированный набор ботов, развёрнутых вместе | 23/23 проверки (parse / identity / degrade / scale) |
| 2 | **Динамический реестр** — `BotManager::add($name, new Telegram($token))` во время выполнения | ваша БД/панель конфигурации; передаются в процесс | боты, создаваемые через админ-панель, боты на каждого арендатора | проверки идентичности + делегированной отправки |
| 3 | **Управляемые боты** — дочерние токены запрашиваются вживую у Telegram (следующий раздел) | **нигде на диске** | бот-менеджер, создающий дочерних ботов от имени пользователей | набор TM-2, 8/8 |

Правила, которые доказывает живой тестовый набор (2026-10-11, два реальных бота + синтетические записи):

- некорректные записи `BOT_EXTRA_BOTS` логируются и **пропускаются — загрузка никогда не падает**;
- мёртвый/отозванный токен падает чисто (`ok=false`, `Unauthorized`) и никогда не отравляет
  других ботов: `get('dead')` даёт ошибку, `get('alive')` и `main` остаются здоровыми;
- `main` зарезервирован; дубликаты имён разрешаются по принципу «последний побеждает» с предупреждением;
- собственное двоеточие токена переживает разбиение `name:token` (только по первому двоеточию);
- изоляция идентичностей: `getMe()` каждого зарегистрированного экземпляра совпадает с id-префиксом
  его токена; стек токенов — на каждый экземпляр (switch/restore на `main` оставляет
  `second` нетронутым);
- поиск в реестре — O(1): 10 000 вызовов `get()` при 32 зарегистрированных ботах примерно за 1 мс.

Замечание о вебхуках: в режимах `webhook_*` каждое обновление, попадающее в `webhook.php`,
обрабатывается от личности **главного** бота (один общий `BOT_WEBHOOK_SECRET`).
Чтобы обслуживать несколько ботов через вебхуки, вам **не** нужна отдельная директория
на каждого бота — паттерн `secret_token` из следующего раздела обслуживает
**любое количество ботов из одного-единственного файла вебхука**, проверено вживую.

## Один файл вебхука, много ботов — паттерн `secret_token`

Вам НЕ нужна отдельная папка на каждого бота. **Один-единственный файл вебхука может
обслуживать любое количество ботов.** Вся хитрость — в параметре `secret_token`
метода `setWebhook`:

1. Выберите **разный случайный секрет для каждого бота** (допускаются только буквы,
   цифры, `_` и `-`).
2. Зарегистрируйте **один и тот же URL вебхука** для каждого бота, каждый со своим
   секретом:
   `setWebhook?url=https://example.com/hook.php&secret_token=<this-bots-secret>`
3. С каждым обновлением Telegram отправляет этот секрет обратно в заголовке
   `X-Telegram-Bot-Api-Secret-Token`.
4. Ваш файл читает заголовок, находит секрет в небольшом реестре
   (`secret → bot token`) и обрабатывает обновление от личности этого бота.

```text
             ┌─ бот A: setWebhook(url=hook.php, secret=SECRET_A)
 Telegram ───┤
             └─ бот B: setWebhook(url=hook.php, secret=SECRET_B)
                         │   POST + header X-Telegram-Bot-Api-Secret-Token
                         ▼
               ┌───────────────────┐   SECRET_A → токен A → действует как бот A
               │     hook.php      │
               │  реестр:          │
               │  секрет → токен   │   SECRET_B → токен B → действует как бот B
               └───────────────────┘
```

Почему это рекомендуемый способ запуска фермы ботов:

- **токен бота никогда не появляется в URL** — он не может утечь в логи доступа,
  историю браузера или прокси;
- секрет заодно служит **проверкой подлинности** — запрос без правильного секрета
  исходит не от Telegram; ответьте `403` и отбросьте его;
- **добавление бота #N+1 стоит одного вызова `setWebhook` и одной строки в реестре** —
  никаких новых файлов, никакого нового деплоя.

Живое доказательство (2026-10-11, два реальных бота, ОДИН файл, реальный пользовательский трафик):

| Событие | Маршрутизированная идентичность | Результат |
|---|---|---|
| реальный `/start` боту B | @instaroonxbot | ответ отправлен, `ok:true` |
| реальное нажатие на инлайн-кнопку бота B (×2) | @instaroonxbot | `answerCallbackQuery` + ответ, `ok:true` |
| реальное нажатие на инлайн-кнопку бота A | @emojiCustom_bot | `answerCallbackQuery` + ответ, `ok:true` |
| синтетический POST с секретом A / секретом B | каждый раз правильный бот | ответ отправлен, `ok:true` |

7/7 доставок — каждое обновление попало в один и тот же файл, и каждый ответ нёс
правильную идентичность бота. Токен бота ни разу не оказался ни в одном URL или заголовке.

Правила ужесточения для продакшена:

- секрет **и есть ключ маршрутизации** — он должен быть уникальным для каждого бота;
- генерируйте его случайно, 32+ символа из `[A-Za-z0-9_-]` (Telegram отклоняет
  другие символы); секрет из 2 символов — это фактически отсутствие секрета;
- отклоняйте неизвестные или отсутствующие секреты с `403`, прежде чем трогать
  что-либо ещё;
- никогда не логируйте токены; логируйте максимум короткий префикс секрета;
- ротация секрета = снова выполнить `setWebhook` для этого бота (занимает секунды).

## Управляемые боты (Managed Bots, Bot API 9.6)

Telegram Bot API 9.6 (2026-04-03) добавил **управляемых ботов (Managed Bots)**: бот
с `can_manage_bots` (включается в Mini App @BotFather) может иметь других ботов,
создаваемых и управляемых под ним. Дочерний токен никогда не нужно хранить —
менеджер запрашивает его вживую через `getManagedBotToken(user_id)`.

Поддержка во фреймворке (v2.4.x):

| Элемент API (Bot API 9.6) | Поверхность фреймворка |
|---|---|
| `User.can_manage_bots` (getMe) | `$tg->callRaw('getMe')->result->can_manage_bots` |
| обновление `managed_bot` (`ManagedBotUpdated`) | диспетчеризуется в `onManagedBot($managedBot, $tg)` — метод добавлен в белый список плагинов |
| `KeyboardButtonRequestManagedBot` | `Keyboard::reply()->requestManagedBot($text, $requestId, $suggestedName, $suggestedUsername)` |
| `getManagedBotToken` / `replaceManagedBotToken` / `get·setManagedBotAccessSettings` | `BotManager::registerManagedBot()` / `refreshManagedBot()` / `managedBotAccessSettings()` |
| поле сообщения `ManagedBotCreated` | видно в полезной нагрузке внутри `onMessage` |

Сквозной сценарий (набросок плагина):

```php
use alirezax5\TelegramBase\App\Bot\BotManager;
use alirezax5\TelegramBase\App\Button\Keyboard;

// 1) offer creation (private chats only)
$tg->sendMessage($chatId, 'Create your own bot:', [
    'reply_markup' => Keyboard::reply()
        ->requestManagedBot('➕ Create my bot', 1, 'MyHelperBot', 'my_helper_bot')
        ->toArray(),
]);

// 2) the user completes the flow in Telegram → managed_bot update arrives
public function onManagedBot($managedBot, $tg): void
{
    // fetches the child token live (getManagedBotToken) and registers it
    BotManager::getInstance()->registerManagedBotFromUpdate($managedBot);
}

// 3) use the child bot — registered under its bot id
BotManager::getInstance()->get((string) $managedBot->bot->id)
    ->sendMessage($chatId, 'hello from the child bot');
```

Предварительные требования (действия владельца, однократно):

1. Включите **управление другими ботами** для бота-менеджера в Mini App
   @BotFather — до этого `getMe` сообщает `can_manage_bots: false`, и запрос
   на создание падает.
2. Само создание дочернего бота всегда происходит на стороне Telegram (согласие
   пользователя); фреймворк только получает обновление `managed_bot` и запрашивает
   токен.

Гигиена токенов: управляемые токены живут только в памяти (в реестре) — ничего не
записывается в `.env` или логи. Ротация дочернего токена через
`BotManager::refreshManagedBot($userId, $name)` немедленно отзывает старый токен
и перерегистрирует новый.

### Управляемые боты — живой сквозной прогон (2026-10-11)

После того как владелец включил **управление другими ботами** в Mini App
@BotFather, `getMe` на обоих тестовых ботах переключился на `can_manage_bots: true`,
и весь сценарий был прогнан вживую:

- кнопка создания, собранная через `Keyboard::reply()->requestManagedBot(...)`, была
  отправлена в приватном чате — Telegram принял форму клавиатуры фреймворка;
- деталь, о которой стоит знать: для `KeyboardButtonRequestManagedBot` поле
  `request_id` должно быть **числом (Number)** (в отличие от `request_chat` /
  `request_users`, где это строка (String) — Telegram отклоняет строку с ошибкой
  `Bad Request: can't parse KeyboardButton: Field "request_id" must be a valid Number`);
- как только пользователь завершает форму создания, менеджер получает обновление
  `managed_bot` и запрашивает дочерний токен вживую через
  `getManagedBotToken(user_id)` — после этого демо заставило **дочернего бота
  говорить в чате владельца** с его собственным свежезапрошенным токеном (ноль на диске).

Те же переключатели Mini App на обоих тестовых ботах тоже перевернулись:
`supports_guest_queries`, `has_topics_enabled`,
`supports_join_request_queries`, `can_connect_to_business` → все `true`.

- Реальная структура обновления (захвачено 2026-10-11): `managed_bot.user` = пользователь, создавший дочернего бота (обычный пользователь), `managed_bot.bot` = сам дочерний бот (`{id, is_bot: true, username, ...}`). Передавайте в `getManagedBotToken` именно `managed_bot.bot.id` — id создателя даёт `Bad Request: user is not a bot`. В демо токен дочернего бота был получен вживую, и дочерний бот доставил своему создателю реальное сообщение — ноль токенов на диске.

### Где хранить токены и секреты

| Хранилище | Когда подходит | На что обратить внимание |
|---|---|---|
| **`.env`** (`BOT_TOKEN` + `BOT_EXTRA_BOTS`) | небольшой фиксированный набор ботов | читается только под root; изменения требуют перезапуска |
| **Таблица-реестр в БД** (`bots`: id, name, token, secret, status) | боты добавляются/удаляются во время выполнения, админ-панели | шифруйте колонку токена при хранении (например, sodium); кэшируйте реестр, чтобы одно обновление ≠ один запрос к БД |
| **Управляемые боты (ноль на диске)** | бот-менеджер, создающий дочерних ботов для пользователей | требуется `can_manage_bots`; токен запрашивается вживую через `getManagedBotToken` |
| **Производные секреты (HMAC)** — ничего не хранится | вы контролируете один мастер-ключ | `secret = base64url(hmac_sha256(master_key, 'bot:' . bot_id))`; ротация мастер-ключа означает перерегистрацию каждого вебхука |

Рекомендация для растущей фермы ботов: **реестр в БД (токен зашифрован при
хранении) + кэшированный поиск + маршрутизация `secret_token`**, а для создаваемых
пользователями дочерних ботов — **управляемые боты (Managed Bots)**. `.env` оставьте
только для первого бота-менеджера.

### Раздельное хранение данных каждого бота

Когда много ботов разделяют один деплой, данные каждого бота должны оставаться
эксклюзивными для этого бота. Проставляйте пространство имён с id бота в **каждом
слое хранения** (`b{bot_id}`):

| Слой | Правило |
|---|---|
| Кэш | префикс ключей `b{bot_id}:` (задайте `CACHE_PREFIX` для каждого бота при загрузке) |
| Сессии | область видимости по **id бота + id пользователя** — один и тот же человек, говорящий с двумя ботами, это две разные сессии |
| Смещение getUpdates | **отдельный файл/ключ смещения на каждого бота** — при общем смещении обновления одного бота попадали бы другому |
| Очередь | имя очереди на каждого бота (`tgbase_b{bot_id}_updates`) или помечайте полезные нагрузки тегом `bot_id` |
| Файловое хранилище | `data/bots/{bot_id}/…` |
| Логи | один файл лога на бота (`logs/bot_{id}.log`) |
| База данных | общие таблицы получают колонку `bot_id`; настоящая изоляция = отдельная БД на каждого бота |

Фронт-контроллер вебхука сначала разрешает `secret → bot`, затем загружает
фреймворк с токеном и пространством имён этого бота — все последующие чтения/записи
автоматически остаются внутри собственной песочницы бота.

## Семантика доставки

Мульти-бот-вызовы едут на том же HTTP-клиенте, что и любой другой вызов API:

- повторные попытки/задержки и обработка `retry_after` применяются на каждый экземпляр;
- стек токенов — **состояние на экземпляр** — в воркерах очереди каждое обновление
  обрабатывается свежей диспетчеризацией, поэтому пары switch/restore живут внутри
  времени жизни одного обновления; никогда не полагайтесь на состояние стека между обновлениями;
- в режимах `webhook_*` те же правила действуют в пределах одного FPM-запроса.
