# Вебхук — приём обновлений от Telegram

## Настройка

```dotenv
# .env
BOT_MODE="webhook_direct"          # or webhook_queue
BOT_WEBHOOK_URL="https://yourdomain.com/webhook.php"
BOT_WEBHOOK_SECRET="a-long-random-string"   # openssl rand -hex 32
WEBHOOK_CHECK_IP=true
```

Зарегистрируйте один раз (Telegram требует HTTPS с валидным сертификатом):

```bash
curl "https://api.telegram.org/bot<TOKEN>/setWebhook?url=https://yourdomain.com/webhook.php&secret_token=<SECRET>"
curl "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"   # verify: pending_update_count=0, no last_error
```

Отмените регистрацию (при переключении обратно на polling — сделайте это *до* запуска `bot.php`, иначе два источника обновлений будут бороться за один и тот же поток):

```bash
curl "https://api.telegram.org/bot<TOKEN>/deleteWebhook"
```

## Пять слоёв валидации

Каждый запрос, попадающий в `webhook.php`, проходит через `WebhookDispatcher` в следующем порядке:

1. **Размер тела** — больше 1 МБ → `413`. (Telegram никогда не отправляет полезную нагрузку больше; всё, что крупнее, — не Telegram.)
2. **Белый список IP** — при `WEBHOOK_CHECK_IP=true` запросы с IP вне официальных подсетей Telegram → `403`. Диапазоны — те, что опубликованы в документации Telegram (`149.154.160.0/20`, `91.108.4.0/22`, `91.108.8.0/22`, `91.108.56.0/22`, `91.108.16.0/22`, `95.161.64.0/20`).
3. **Секретный токен** — при установленном `BOT_WEBHOOK_SECRET` заголовок `X-Telegram-Bot-Api-Secret-Token` должен совпасть; сравнение выполняется через `hash_equals()` (защита от timing-атак). Несовпадение → `403`.
4. **Валидация JSON** — тело должно распарситься в объект, содержащий `update_id`. Иначе → `400`.
5. **Маршрутизация** — `webhook_direct` выполняет плагины синхронно и отвечает `200`, только если ничего не выбросило исключение; `webhook_queue` ставит обновление в очередь и сразу отвечает `200`.

Провал валидации никогда не расходует обновление так, чтобы оно терялось — Telegram повторно отправляет обновления, за которые не получил `2xx`.

## За Cloudflare / прокси nginx (важно)

Если запросы Telegram доходят до PHP через Cloudflare (или любой обратный прокси), PHP видит в `REMOTE_ADDR` IP *прокси*, а не Telegram — проверка IP отклонит каждый запрос. Две рабочие схемы:

- **Прокси спереди:** оставьте `WEBHOOK_CHECK_IP=false` и полагайтесь на **секретный токен** как на аутентификацию входящего трафика (сделайте его длинным — 32+ hex-символов). Именно так фреймворк валидировался в продакшен-тестировании.
- **Прокси передаёт реальный IP:** настройте прокси так, чтобы он отправлял `X-Forwarded-For` / `X-Real-IP`, *и* чтобы PHP ему доверял — тогда `WEBHOOK_CHECK_IP=true` работает. Делайте это, только если прокси под вашим контролем, иначе заголовок можно подделать.

Правило большого пальца: **проверка IP = прямая доступность; секрет = доступность через прокси.** Использовать и то и другое тоже можно.

## Поведение режимов на webhook-входе

| `BOT_MODE` | Что делает `webhook.php` |
|------------|--------------------------|
| `webhook_direct` | валидация → `Processor::handle()` → `200` по завершении |
| `webhook_queue` | валидация → постановка в очередь → немедленный `200` |
| `update_direct` | валидация → `Processor::handle()` → `200` (работает, но логирует предупреждение — явно указывайте `webhook_direct`) |
| `update_queue`, `cronjob_*` | `500` + пояснительное сообщение — эти режимы только для CLI |

Последняя строка — это SAPI-защита v2.4.0 ([bot-modes.md](bot-modes.md)): CLI-режим на веб-точке входа больше не может запустить бесконечный цикл внутри вашего PHP-FPM-воркера (что раньше заканчивалось `Read timeout expired` на стороне Telegram и 502 от вашего веб-сервера).

## Семантика ответов — почему важен 200

Telegram повторяет любую доставку вебхука, не получившую `2xx`, с задержкой, на протяжении до нескольких часов. Фреймворк честно использует это:

- `200` отправляется **только после** того, как обновление обработано (direct) или безопасно поставлено в очередь (queue-режим).
- Исключение во время обработки → `500` → Telegram позже доставит повторно → обновление **не теряется**, но *будет обработано дважды*, если первая попытка на самом деле успела завершиться до падения. Это и есть определение доставки at-least-once — см. [reliability.md](reliability.md) о том, как делать хендлеры идемпотентными.
- Воркер, отвечающий минутами, — это баг, а не фича: клиентский таймаут Telegram ~60 с. Выносите медленную работу в `webhook_queue`.

## Регистрация с allowed updates (необязательно)

Ограничьте то, что Telegram вам отправляет, теми типами обновлений, которые ваши плагины реально обрабатывают:

```bash
curl "https://api.telegram.org/bot<TOKEN>/setWebhook?url=...&secret_token=...&allowed_updates=[\"message\",\"edited_message\",\"callback_query\",\"channel_post\",\"edited_channel_post\"]"
```

## Проверки здоровья

`getWebhookInfo` — ваша панель мониторинга. Следите за:

- `pending_update_count` — обновления, скопившиеся у Telegram, потому что ваша конечная точка сбоит/медлит. Устойчивый рост = инцидент.
- `last_error_message` / `last_error_date` — точная причина сбоя доставки (таймауты, ошибки TLS, неверный секрет).

Чек-лист развёртывания для режима вебхука:

1. `webhook.php` доступен по HTTPS (проверьте браузером: пустой GET должен вернуть `400 empty` — это отвечает диспетчер).
2. `BOT_WEBHOOK_SECRET` ≥ 32 случайных символов, одинаковый в `.env` и в `setWebhook`.
3. `WEBHOOK_CHECK_IP` соответствует вашей сетевой топологии (см. раздел о прокси).
4. `getWebhookInfo` чистое после тестового сообщения; побочный эффект плагина виден.
