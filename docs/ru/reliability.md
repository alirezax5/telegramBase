# Надёжность — что на самом деле происходит при падениях

Этот документ необычен для документации фреймворка: всё в нём было **измерено, а не предположено**. Во время интеграционного тестирования (фазы 3.2–3.3) воркеры убивались `SIGKILL` на каждом этапе каждого конвейера — во время fetch, во время отправки в очередь, посреди хендлера, после хендлера, но до ack, до/после записи смещения — и исход каждого сценария был зафиксирован. Эта страница — дистиллированный результат, и он определяет как дизайн фреймворка, так и приведённые ниже советы.

## Гарантии доставки по путям

| Путь | Гарантия | Почему | Окно дубликатов |
|------|----------|--------|-----------------|
| Polling (`update_direct`) | **at-least-once** | смещение `getUpdates` сохраняется только *после* возврата `Processor::handle()` | падение после побочных эффектов, до записи смещения |
| Webhook (`webhook_direct`) | **at-least-once** | `200` отправляется только после возврата `handle()`; всё остальное Telegram повторяет | падение после побочных эффектов, до 200 |
| Webhook → очередь (`webhook_queue`) | **at-least-once в брокер** | `200` только после успешной постановки в очередь | недоступность брокера между постановкой в очередь и 200 |
| Консюмер очереди — **RabbitMQ** (v2.4.0) | **at-least-once** | ack-after-process: неподтверждённые сообщения брокер доставляет повторно | падение после обработки, до ack |
| Консюмер очереди — Redis / JSON / Memcached | **at-most-once** | разрушающий pop — сообщение удаляется в момент pop | нет (падение посреди обработки теряет задачу) |
| Очередь повторов | **at-least-once, ограниченная** | элементы повторно диспетчеризуются с задержкой до `RETRY_MAX_ATTEMPTS` | как у родительского пути |

Два честных наблюдения из crash-тестов:

- **Exactly-once не существует.** Ни в TelegramBase, ни в любой системе, построенной поверх сети. Вы выбираете между «никогда не терять» (at-least-once, дубликаты возможны при падении) и «никогда не дублировать» (at-most-once, потери возможны при падении). Фреймворк даёт вам оба семейства и документирует, что есть что.
- **Окна дубликатов узки, но реальны.** Они открываются только при падении ровно в неправильный момент. Они закрываются идемпотентными хендлерами.

## Идемпотентность хендлеров (практические 90%)

At-least-once болезненна, только если одно и то же обновление *дважды приводит к действию*. Одна защита делает каждое окно безвредным:

```php
public function onMessage($message, Telegram $tg): void
{
    $update  = $tg->getInputData();
    $uId     = $update->update_id ?? null;

    // Cheap, atomic, per-update marker — works with any cache driver.
    if (!empty(cache()->get("upd:{$uId}"))) {
        return;                       // already processed (redelivery) — skip
    }

    // ... do the actual work ...

    cache()->set("upd:{$uId}", 1, 3600);   // remember for an hour
}
```

По возможности сохраняйте маркер *до* необратимых побочных эффектов и смиритесь с тем, что падение между маркером и побочным эффектом превращает дубликат в потерю — выбирайте компромисс, подходящий для конкретного действия (отправить сообщение дважды обычно дешевле, чем не отправить его вовсе).

## Поведение при падениях по компонентам

| Компонент | Сценарий падения | Наблюдаемое поведение |
|-----------|------------------|------------------------|
| Polling-воркер (`update_direct`) | `SIGKILL` посреди батча | смещение не изменилось → те же обновления доставляются повторно после перезапуска → обрабатываются заново (важна идемпотентность) |
| Polling-воркер | `SIGKILL` между батчами | чисто; в худшем случае текущее обновление доставляется повторно |
| Фетчер очереди (`queue.php`) | `SIGKILL` после pop, до push | обновление всё ещё на стороне Telegram (смещение не продвинуто) → доставится повторно |
| Фетчер очереди | `SIGKILL` после push, до записи смещения | обновление в брокере **и** всё ещё на стороне Telegram → перезапуск продюсера задублирует его в брокере (ограничивается `QUEUE_MAX_SIZE`; идемпотентность консюмеров это поглощает) |
| RabbitMQ-воркер (до v2.4.0) | `SIGKILL` посреди обработки | задача **безвозвратно потеряна** (ack уже был отправлен) — исправлено в v2.4.0 |
| RabbitMQ-воркер (v2.4.0+) | `SIGKILL` посреди обработки | задача **доставляется повторно** следующему воркеру (не подтверждена) |
| Redis/JSON-воркер | `SIGKILL` посреди обработки | задача теряется безвозвратно (разрушающий pop) — так задумано, задокументировано |
| Webhook (FPM) | хендлер превышает ~60 с | Telegram уходит в таймаут и повторяет; если хендлер в итоге завершится, повтор задублирует его — держите обработку вебхука быстрой или используйте `webhook_queue` |
| Брокер недоступен (любой queue-режим) | соединение отклонено | воркеры выдерживают экспоненциальную паузу (1 с → 60 с), переподключаются и продолжают; фетчер сохраняет смещение, пока отправки не увенчаются успехом |

## Ограниченные ресурсы

- **Очереди ограничены** (`QUEUE_MAX_SIZE`, `RETRY_MAX_SIZE`): при заполнении отправки отклоняются и логируются — сбой не сможет молча забить ваш диск.
- **Память ограничена**: polling-воркер самоперезапускается каждые `POLLING_RESTART_INTERVAL` батчей (настраивается, `0` отключает).
- **Логи защищены от path traversal**: `LOG_DIR`/`LOG_FILE` не могут указывать за пределы проекта.

## Таксономия ошибок, используемая очередью повторов

`RetryableException::isRetryable()` классифицирует ошибки так, чтобы повторялись только *временные* сбои:

- HTTP `429 Too Many Requests` (с учётом Telegram `parameters.retry_after`, когда он присутствует)
- HTTP `5xx` / «ошибка сервера»
- таймауты (`timeout`, `timed out`, `connect`)
- `cURL error N`
- любой подкласс `RetryableException`, который вы выбрасываете сами

Всё остальное (400 «chat not found», 403 «bot blocked», ...) — постоянно: логируется, не повторяется.

## Проверка собственной надёжности

Поставляемый набор тестов включает относящиеся к падениям примитивы (атомарность хранения смещения, драйверы очереди, жизненный цикл повторов, пути валидации вебхук-диспетчера):

```bash
php tests/run.php --filter=Queue     # queue driver behaviour
php tests/run.php --filter=Offset    # offset storage
php tests/run.php --filter=Retry     # retry lifecycle
php tests/run.php --filter=Webhook   # webhook validation layers
```

Для сквозной уверенности повторите интеграционный подход на собственном развёртывании: зарегистрируйте вебхук, отправьте маркерное сообщение, выполните `kill -9` воркера посреди полёта и проверьте повторную доставку в `getWebhookInfo` / логах.
