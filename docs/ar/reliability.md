# الموثوقية — ما الذي يحدث فعلًا عند الانهيارات

هذه الوثيقة غير عادية بين وثائق إطار عمل: كل ما فيها كان **مُقاسًا لا مفترضًا**. أثناء الاختبارات التكاملية (المرحلتان 3.2–3.3) قُتل العمال بـ `SIGKILL` في كل مرحلة من مراحل كل خط معالجة — أثناء الجلب، وأثناء الدفع إلى القائمة، وفي منتصف المعالج، وبعد المعالج وقبل الإقرار، وقبل/بعد كتابات الإزاحة — وسُجّلت نتيجة كل سيناريو. هذه الصفحة هي النتيجة المقطّرة، وهي تقود تصميم الإطار والنصائح الواردة أدناه معًا.

## ضمانات التسليم لكل مسار

| المسار | الضمانة | السبب | نافذة التكرار |
|------|-----------|-----|------------------|
| الاستطلاع (`update_direct`) | **at-least-once** | تُخزَّن إزاحة `getUpdates` بشكل دائم فقط *بعد* أن تعود `Processor::handle()` | انهيار بعد الآثار الجانبية وقبل كتابة الإزاحة |
| الويب هوك (`webhook_direct`) | **at-least-once** | تُرسَل `200` فقط بعد أن تعود `handle()`؛ ويعيد Telegram محاولة أي شيء آخر | انهيار بعد الآثار الجانبية وقبل 200 |
| الويب هوك ← قائمة انتظار (`webhook_queue`) | **at-least-once إلى الوسيط** | `200` فقط بعد إضافة ناجحة إلى القائمة | تعطّل الوسيط بين الإضافة و200 |
| مستهلك القائمة — **RabbitMQ** (v2.4.0) | **at-least-once** | إقرار بعد المعالجة: يعيد الوسيط تسليم الرسائل غير المُقرَّ بها | انهيار بعد المعالجة وقبل الإقرار |
| مستهلك القائمة — Redis / JSON / Memcached | **at-most-once** | سحب مُدمِّر — تُزال الرسالة لحظة السحب | لا شيء (انهيار أثناء المعالجة يفقد المهمة) |
| قائمة إعادة المحاولة | **at-least-once، محدودة** | تُعاد توزيع العناصر بتراجع تدريجي حتى `RETRY_MAX_ATTEMPTS` | مثل مسارها الأصلي |

ملاحظتان صادقتان من اختبارات الانهيار:

- **exactly-once غير موجودة.** لا في TelegramBase ولا في أي نظام مبني فوق شبكة. تختار بين «ألا تفقد أبدًا» (at-least-once، مع تكرار ممكن عند الانهيار) و«ألا تكرر أبدًا» (at-most-once، مع فقد ممكن عند الانهيار). يمنحك الإطار العائلتين معًا ويوثّق أيّهما أيّ.
- **نوافذ التكرار ضيقة لكنها حقيقية.** لا تنفتح إلا عند انهيار في اللحظة الخاطئة بالضبط. وتُغلق بمعالجات قابلة لإعادة التنفيذ بأمان.

## جعل المعالجات قابلة لإعادة التنفيذ بأمان (الـ 90% العملية)

تكون at-least-once مؤلمة فقط عندما تُطبَّق على التحديث نفسه إجراءات *مرتين*. حارس واحد يجعل كل نافذة غير مؤذية:

```php
public function onMessage($message, Telegram $tg): void
{
    $update  = $tg->getInputData();
    $uId     = $update->update_id ?? null;

    // Cheap, atomic, per-update marker — works with any cache driver.
    if (!empty(cache()->get("upd:{$uId}"))) {
        return;                       // already processed (redelivery) — skip
    }

    // ... do the actual work ...

    cache()->set("upd:{$uId}", 1, 3600);   // remember for an hour
}
```

خزّن العلامة *قبل* الآثار الجانبية غير القابلة للتراجع كلما أمكن، وتقبّل أن انهيارًا بين العلامة والأثر الجانبي يحوّل تكرارًا إلى فقد — اختر المقايضة التي تناسب الإجراء (إرسال رسالة مرتين أرخص عادةً من عدم إرسالها إطلاقًا).

## سلوك الانهيار حسب المكوّن

| المكوّن | سيناريو الانهيار | السلوك المُلاحَظ |
|-----------|---------------|--------------------|
| عامل الاستطلاع (`update_direct`) | `SIGKILL` في منتصف دفعة | الإزاحة لا تتغير ← تُعاد تسليم التحديثات نفسها عند إعادة التشغيل ← تُعالَج مجددًا (قابلية إعادة التنفيذ مهمة) |
| عامل الاستطلاع | `SIGKILL` بين الدفعات | نظيف؛ على الأكثر يعاد تسليم التحديث الجاري |
| جالب القائمة (`queue.php`) | `SIGKILL` بعد السحب وقبل الدفع | التحديث ما يزال في جانب Telegram (الإزاحة لم تتقدم) ← يُعاد تسليمه |
| جالب القائمة | `SIGKILL` بعد الدفع وقبل كتابة الإزاحة | التحديث في الوسيط **و**ما يزال في جانب Telegram ← إعادة تشغيل المنتج ستكرره في الوسيط (محدود بـ `QUEUE_MAX_SIZE`؛ قابلية إعادة التنفيذ لدى المستهلكين تستوعبه) |
| عامل RabbitMQ (قبل v2.4.0) | `SIGKILL` أثناء المعالجة | تُفقد المهمة **بشكل دائم** (كان الإقرار قد أُرسل بالفعل) — أُصلح في v2.4.0 |
| عامل RabbitMQ (v2.4.0 وما بعده) | `SIGKILL` أثناء المعالجة | تُعاد تسليم المهمة إلى العامل التالي (غير مُقرَّ بها) |
| عامل Redis/JSON | `SIGKILL` أثناء المعالجة | تُفقد المهمة بشكل دائم (سحب مُدمِّر) — بالتصميم، وموثّق |
| الويب هوك (FPM) | معالج يتجاوز ~60 ثانية | تنقضي مهلة Telegram ويعيد المحاولة؛ إذا اكتمال المعالج لاحقًا، يكرر الـ retry ذلك — أبقِ معالجة الويب هوك سريعة أو استخدم `webhook_queue` |
| الوسيط متوقف (أي وضع قائمة انتظار) | رفض الاتصال | يتراجع العمال أُسّيًا (1 ثانية ← 60 ثانية)، ويعيدون الاتصال والاستئناف؛ يحتفظ الجالب بالإزاحة حتى تنجح عمليات الدفع |

## موارد محدودة

- **قوائم الانتظار محدودة** (`QUEUE_MAX_SIZE`، `RETRY_MAX_SIZE`): عند الامتلاء تُرفض عمليات الدفع وتُسجَّل — لا يمكن لعطل أن يملأ قرصك بصمت.
- **الذاكرة محدودة**: يعيد عامل الاستطلاع تشغيل نفسه بعد كل `POLLING_RESTART_INTERVAL` دفعة (قابل للضبط، و`0` يُلغي ذلك).
- **السجلات آمنة ضد تجاوز المسار**: لا يمكن لـ `LOG_DIR`/`LOG_FILE` أن يشيرا إلى خارج المشروع.

## تصنيف الأخطاء المستخدم في قائمة إعادة المحاولة

يصنّف `RetryableException::isRetryable()` الأخطاء بحيث لا تُعاد المحاولة إلا للإخفاقات *العابرة*:

- HTTP ‏`429 Too Many Requests` (مع مراعاة `parameters.retry_after` من Telegram عند وجوده)
- HTTP ‏`5xx` / «خطأ خادم»
- انتهاء المهل (`timeout`، `timed out`، `connect`)
- `cURL error N`
- أي صنف فرعي من `RetryableException` ترمه بنفسك

كل ما عدا ذلك (400 «المحادثة غير موجودة»، و403 «البوت محظور»، ...) دائم — يُسجَّل ولا تُعاد المحاولة.

## اختبار وضعيتك الموثوقية الخاصة

تتضمن مجموعة الاختبارات المشحونة الأدوات الأساسية المتعلقة بالانهيارات (ذرّية تخزين الإزاحة، مُشغِّلات قوائم الانتظار، دورة حياة إعادة المحاولة، مسارات تحقق موزّع الويب هوك):

```bash
php tests/run.php --filter=Queue     # queue driver behaviour
php tests/run.php --filter=Offset    # offset storage
php tests/run.php --filter=Retry     # retry lifecycle
php tests/run.php --filter=Webhook   # webhook validation layers
```

وللثقة الشاملة من طرف إلى طرف، كرّر منهج التكامل على نشرتك الخاصة: سجّل الويب هوك، وأرسل رسالة علامة، ونفّذ `kill -9` على العامل في منتصف عمله، وتحقق من إعادة التسليم في `getWebhookInfo` / السجلات.
