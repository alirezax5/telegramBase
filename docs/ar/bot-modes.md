# أوضاع البوت — الطرق الست لتشغيل بوت TelegramBase

القيمة `BOT_MODE` في `.env` هي أهم قيمة إعدادات على الإطلاق. فهي تقرر *كيف تصل التحديثات* (استطلاع مقابل ويب هوك) و*كيف تُعالَج* (مباشرة مقابل عبر قائمة انتظار).

## الأوضاع

| الوضع | مصدر التحديثات | المعالجة | العمليات التي تشغّلها |
|------|--------------|------------|-------------------|
| `update_direct` *(الافتراضي)* | استطلاع طويل عبر `getUpdates` | مباشرة، في العملية نفسها | `php bot.php` تحت مشرف عمليات |
| `update_queue` | استطلاع طويل عبر `getUpdates` | غير متزامنة عبر قائمة انتظار | `php queue.php` (جالب) + واحدة أو أكثر من `php bot.php` (عمال) |
| `webhook_direct` | POST من ويب هوك Telegram | مباشرة، داخل طلب HTTP | خادم الويب فقط (`webhook.php`) |
| `webhook_queue` | POST من ويب هوك Telegram | غير متزامنة عبر قائمة انتظار | خادم الويب (`webhook.php`) + عامل أو أكثر من `php bot.php` |
| `cronjob_update` | `getUpdates` (استطلاع) | مباشرة، **شيطان (daemon) ذاتي الشفاء** — النبضة الأولى تبدأ حلقة لا نهائية، والنبضات اللاحقة لا تفعل شيئًا ما دام حيًّا | crontab `* * * * * php bin/scheduler.php` |
| `cronjob_queue` | قائمة الانتظار فقط (بلا استطلاع لـ Telegram) | دفعة غير متزامنة — كل نبضة تستهلك حتى `CRON_MAX_TIME` (الافتراضي 50 ثانية) ثم تخرج | crontab + فتحات `CRON_WORKER` |

النموذج الذهني:

- أوضاع **`update_*` / `cronjob_*`** تسحب التحديثات بنفسها (خادمك هو من يتحدث إلى Telegram).
- أوضاع **`webhook_*`** تستقبل التحديثات (Telegram هو من يتحدث إلى خادمك).
- الأوضاع **`*_direct`** تعالج التحديث في مكانه الذي وصل إليه — الأسهل، ومناسب لمعظم البوتات.
- الأوضاع **`*_queue`** تفصل الاستقبال عن المعالجة — استخدمها عندما تكون المعالجات بطيئة (تحميل ملفات، واجهات API خارجية) أو عندما تريد توسعًا أفقيًا.
- أوضاع **`cronjob_*`** تعمل من crontab عادي — بلا مشرف عمليات، وبلا systemd، وبلا Docker.

## أوضاع cron بالتفصيل

يشارك كلا وضعي cron الآلية الأمنية نفسها: في كل نبضة يحاول الإطار الحصول على **فتحة عامل** — قفل حصري `flock()` على ملف قفل تحت `data/cron-slots/` (`WorkerLocker`). إذا كانت كل فتحات `CRON_WORKER` مشغولة، تسجّل النبضة الرسالة `All N worker slots busy` وتخرج خلال أجزاء من الثانية — لا يمكن للنبضات المتزامنة أبدًا أن تعالج أي شيء مرتين.

### `cronjob_update` — شيطان ذاتي الشفاء، لا دفعة

رغم الاسم، فإن النبضة **لا** تشغّل «دفعة واحدة». النبضة الأولى تحصل على الفتحة وتبدأ حلقة الاستطلاع اللانهائية نفسها المستخدمة في `update_direct` (`set_time_limit(0)` + استطلاع طويل)، ولا تنتهي النبضة قطعًا — وهذا مقصود:

1. النبضة 1 ← يبدأ الشيطان، وتظل الفتحة مقفلة.
2. النبضات 2..N ← تجد الفتحة مشغولة فتخرج خلال أجزاء من الثانية (مُقاس: ~30–45 مللي ثانية). هذا *أمر طبيعي*، وليس خطأ.
3. يموت الشيطان (انهيار، OOM، إعادة تشغيل) ← تبدأ نبضة cron التالية شيطانًا جديدًا تلقائيًا. **يعمل cron بوصفه المشرف.**

تم التحقق مباشرة: شيطان بدأ في 09:24:01، وعالج رسالة حقيقية مباشرة، ونجا عبر عدة حدود دقائق، وأُوقف بأمان عند SIGTERM خلال دورة استطلاع طويلة واحدة (~12 ثانية — يُستجاب لإشارة التوقف بمجرد أن يعود الاستطلاع الطويل الجاري)، وأطلق القفل، وأعادت النبضة التالية مباشرة تشغيله.

### `cronjob_queue` — عامل دفعات محدود

كل نبضة تحصل على فتحة وتستهلك من قائمة الانتظار لمدة لا تتجاوز `CRON_MAX_TIME` ثانية (الافتراضي 50)، ثم تخرج بنظافة مع الرسالة `Limited worker finished: N updates`. لا شيء يستطلع Telegram في هذا الوضع — يجب أن يُغذّى الوسيط بمنتج (`webhook_queue`، أو تشغيلك الخاص لـ `queue.php`).

تم التحقق مباشرة: رسالة حقيقية دُفعت إلى RabbitMQ في 09:22:49 سُحبت ووزّعتها النبضة التي كانت داخل نافذتها ذات الـ 50 ثانية بالفعل (`onMessage` للإضافة عند 09:22:49.6، والرسالة `Limited worker finished: 1 updates` عند 09:22:51)، وعادت قائمة الانتظار إلى 0/0. دلالات التسليم موروثة من مُشغِّل قائمة الانتظار — at-least-once مع RabbitMQ منذ v2.4.0.

### إعدادات cron

| متغير البيئة | الافتراضي | المعنى |
|-----|---------|---------|
| `CRON_WORKER` | `1` | عدد فتحات العمال المتزامنة (ملفات flock في `data/cron-slots/`) |
| `CRON_MAX_TIME` | `50` | نافذة دفعة `cronjob_queue` بالثواني — أبقها أقل من فترة cron لديك كي لا تتداخل النبضات |

## نقاط الدخول وحارس SAPI

| الملف | يعمل بوصفه | الغرض |
|------|---------|---------|
| `bot.php` | CLI | الاستطلاع (`update_direct`)، مستهلك قائمة الانتظار (`*_queue`)، استدعاءات cron |
| `queue.php` | CLI | *منتج* قائمة الانتظار — يستطلع Telegram استطلاعًا طويلًا ويدفع التحديثات إلى قائمة الانتظار (`update_queue`) |
| `webhook.php` | HTTP | يستقبل طلبات POST من ويب هوك Telegram (`webhook_*`) |
| `bin/tgbase` | CLI | التشخيص، وتوليد الهياكل، وترحيلات قاعدة البيانات |
| `bin/scheduler.php` | CLI | مشغّل نبضات cron (`cronjob_*` + المهام المجدولة) |

**مهم — حارس SAPI (v2.4.0):** طلب HTTP لا يمكنه إلا خدمة أعمال من نوع الويب هوك. إذا نُفِّذ `webhook.php` بينما `BOT_MODE` في وضع CLI فقط، يرفض الإطار تشغيل حلقة لا نهائية داخل عامل الويب لديك:

| `BOT_MODE` على `webhook.php` | السلوك |
|------------------------------|-----------|
| `webhook_direct` | تحقق ← معالجة مباشرة ← `200` |
| `webhook_queue` | تحقق ← إضافة إلى قائمة الانتظار ← `200` |
| `update_direct` | تحقق ← معالجة مباشرة ← `200` (تُسجَّل رسالة تحذير — على الأرجح كنت تقصد `webhook_direct`) |
| `update_queue`، `cronjob_*` | **HTTP 500** مع رسالة توضيحية — لا حلقة، ولا تعليق |

الخلفية: قبل وجود هذا الحارس، كان توجيه الويب هوك إلى بوت مُهيَّأ لـ `update_direct` يبدأ بصمت حلقة `getUpdates` لا نهائية داخل عامل PHP-FPM. لم يكن Telegram يتلقى أبدًا استجابة (`Read timeout expired` ← إعادة محاولة لا نهائية) وكان FPM يقتل العامل عند `request_terminate_timeout` (502). يحوّل الحارس هذا التعليق الصامت إلى فشل صاخب وسريع. يمكنك اختبار منطق الكشف مباشرة عبر `Core::isHttpSapi($sapi)`.

> قاعدة عامة: **أوضاع CLI تعمل من الطرفية، وأوضاع الويب هوك تعمل من الويب.** الإطار يفرض هذا الحد عنك.

## دلالات التسليم في لمحة

| المسار | الضمانة | نافذة التكرار |
|------|-----------|------------------|
| `webhook_direct` | at-least-once (يعيد Telegram المحاولة حتى يحصل على 2xx) | انهيار *بعد* `handle()` وقبل 200 |
| `update_direct` | at-least-once (لا تتقدم الإزاحة إلا بعد المعالجة) | انهيار *بعد* الآثار الجانبية وقبل كتابة الإزاحة |
| `webhook_queue` (جانب المنتج) | التحديث موجود في الوسيط بمجرد حصولك على 200 | إعادة محاولة الإضافة إلى القائمة عند فشل الوسيط |
| مستهلك قائمة الانتظار — **RabbitMQ** | at-least-once (إقرار بعد المعالجة، v2.4.0) | انهيار بين المعالجة والإقرار |
| مستهلك قائمة الانتظار — Redis / JSON / Memcached | at-most-once (سحب مُدمِّر — تختفي المهمة لحظة السحب) | انهيار أثناء المعالجة يفقد المهمة |

أدلة اختبارات الانهيار الكاملة وإرشادات الالتزام (idempotency): [reliability.md](reliability.md).

يتصرف `cronjob_update` تمامًا مثل `update_direct` (رسالة واحدة تُعالج مباشرة قبل أن تتقدم الإزاحة)؛ ويتصرف `cronjob_queue` تمامًا مثل مستهلك قائمة الانتظار الخاص بمُشغِّله (at-least-once مع RabbitMQ، وat-most-once مع Redis/JSON/Memcached).

## اختيار الوضع — نصائح عملية

- **البوتات الصغيرة، ولوحات المعلومات، والنماذج الأولية** ← `update_direct`. عملية واحدة، وبنية تحتية صفرية.
- **المعالجات البطيئة (معالجة ملفات، واجهات API خارجية)، وعدة نسخ** ← `webhook_queue` أو `update_queue` مع Redis/RabbitMQ.
- **الاستضافة المشتركة بلا شياطين CLI** ← `cronjob_update` (يصبح crontab هو المشرف) أو `webhook_direct`.
- **تريد exactly-once؟** لا أحد يملكها. يمنحك TelegramBase مسارات *at-least-once* لا تفقد تحديثات أبدًا، ومسارات *at-most-once* لا تكرر أبدًا — اختر حسب حالة الاستخدام، واجعل معالجاتك قابلة لإعادة التنفيذ بأمان (انظر [reliability.md](reliability.md)).
