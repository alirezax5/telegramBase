# قابلیت اطمینان — وقتی چیزها کرش می‌کنند واقعاً چه اتفاقی می‌افتد

این سند برای مستندات یک فریمورک غیرمعمول است: همه‌چیز در آن **اندازه‌گیری شده، نه حدس زده‌شده**. در طول تست یکپارچگی (فازهای 3.2–3.3)، ورکرها در هر مرحله از هر پایپ‌لاین با `SIGKILL` کشته می‌شدند — حین fetch، حین push به صف، وسط هندلر، بعد از هندلر اما قبل از ack، قبل/بعد از نوشتن آفست — و نتیجهٔ هر سناریو ثبت می‌شد. این صفحه نتیجهٔ تقطیرشدهٔ آن است و هم طراحی فریمورک و هم توصیه‌های زیر از آن تغذیه می‌کند.

## تضمین‌های تحویل به تفکیک مسیر

| مسیر | تضمین | چرا | پنجرهٔ تکرار |
|------|-----------|-----|------------------|
| Polling (`update_direct`) | **at-least-once** | آفست `getUpdates` فقط *بعد از* بازگشت `Processor::handle()` ذخیره می‌شود | کرش بعد از اثرات جانبی، قبل از نوشتن آفست |
| وبهوک (`webhook_direct`) | **at-least-once** | `200` فقط بعد از بازگشت `handle()` فرستاده می‌شود؛ تلگرام هر چیز دیگری را دوباره تلاش می‌کند | کرش بعد از اثرات جانبی، قبل از 200 |
| وبهوک → صف (`webhook_queue`) | **at-least-once تا رسیدن به برکر** | `200` فقط بعد از enqueue موفق | قطعی برکر بین enqueue و 200 |
| مصرف‌کنندهٔ صف — **RabbitMQ** (نسخهٔ v2.4.0) | **at-least-once** | ack بعد از پردازش: پیام‌های ackنشده توسط برکر دوباره تحویل داده می‌شوند | کرش بعد از هندل، قبل از ack |
| مصرف‌کنندهٔ صف — Redis / JSON / Memcached | **at-most-once** | pop مخرب — پیام در لحظهٔ pop حذف می‌شود | هیچ (کرش وسط پردازش، کار را از دست می‌دهد) |
| صف retry | **at-least-once، محدود** | آیتم‌ها با backoff تا `RETRY_MAX_ATTEMPTS` دوباره توزیع می‌شوند | همان مسیر والدش |

دو مشاهدهٔ صادقانه از crash-testها:

- **exactly-once وجود ندارد.** نه در TelegramBase و نه در هیچ سیستمی که روی یک شبکه ساخته شده باشد. شما بین «هرگز از دست نده» (at-least-once، با امکان تکرار هنگام کرش) و «هرگز تکرار نکن» (at-most-once، با امکان از دست رفتن هنگام کرش) انتخاب می‌کنید. فریمورک هر دو خانواده را در اختیارتان می‌گذارد و مستند می‌کند کدام کدام است.
- **پنجره‌های تکرار باریک‌اند اما واقعی‌اند.** فقط با یک کرش در دقیقاً بدترین لحظه باز می‌شوند و با هندلرهای idempotent بسته می‌شوند.

## idempotent‌کردن هندلرها (۹۰٪ عملی ماجرا)

at-least-once فقط زمانی دردناک است که یک آپدیت *دو بار* مورد عمل قرار بگیرد. یک محافظ، همهٔ پنجره‌ها را بی‌ضرر می‌کند:

```php
public function onMessage($message, Telegram $tg): void
{
    $update  = $tg->getInputData();
    $uId     = $update->update_id ?? null;

    // Cheap, atomic, per-update marker — works with any cache driver.
    if (!empty(cache()->get("upd:{$uId}"))) {
        return;                       // already processed (redelivery) — skip
    }

    // ... do the actual work ...

    cache()->set("upd:{$uId}", 1, 3600);   // remember for an hour
}
```

نشانه را هرجا ممکن است *قبل از* اثرات جانبیِ برگشت‌ناپذیر ذخیره کنید، و بپذیرید که کرش بین نشانه و اثر جانبی، یک تکرار را به یک از دست رفتن تبدیل می‌کند — بسته به نوع عمل، مناسب‌ترین معامله را انتخاب کنید (فرستادن یک پیام دو بار معمولاً ارزان‌تر از هرگز فرستادن آن است).

## رفتار هنگام کرش، به تفکیک کامپوننت

| کامپوننت | سناریوی کرش | رفتار مشاهده‌شده |
|-----------|---------------|--------------------|
| ورکر polling (`update_direct`) | `SIGKILL` وسط بسته | آفست بدون تغییر → همان آپدیت‌ها بعد از ری‌استارت دوباره تحویل داده می‌شوند → دوباره پردازش می‌شوند (idempotency مهم است) |
| ورکر polling | `SIGKILL` بین بسته‌ها | تمیز؛ حداکثر آپدیت جاری دوباره تحویل داده می‌شود |
| fetcher صف (`queue.php`) | `SIGKILL` بعد از pop، قبل از push | آپدیت هنوز در سمت تلگرام است (آفست جلو نرفته) → دوباره تحویل داده می‌شود |
| fetcher صف | `SIGKILL` بعد از push، قبل از نوشتن آفست | آپدیت هم در برکر است **و هم** هنوز در سمت تلگرام → ری‌استارت تولیدکننده آن را دوباره در برکر می‌گذارد (محدود به `QUEUE_MAX_SIZE`؛ idempotency مصرف‌کننده‌ها آن را جذب می‌کند) |
| ورکر RabbitMQ (قبل از v2.4.0) | `SIGKILL` وسط پردازش | کار **برای همیشه از دست می‌رود** (ack قبلاً فرستاده شده بود) — در نسخهٔ v2.4.0 رفع شد |
| ورکر RabbitMQ (نسخهٔ v2.4.0 به بعد) | `SIGKILL` وسط پردازش | کار به ورکر بعدی **دوباره تحویل داده می‌شود** (ackنشده) |
| ورکر Redis/JSON | `SIGKILL` وسط پردازش | کار برای همیشه از دست می‌رود (pop مخرب) — عمدی و مستندشده |
| وبهوک (FPM) | هندلر از ~60 ثانیه تجاوز کند | تلگرام timeout می‌زند و دوباره تلاش می‌کند؛ اگر هندلر در نهایت کامل شود، تلاش مجدد آن را تکرار می‌کند — پردازش وبهوک را سریع نگه دارید یا از `webhook_queue` استفاده کنید |
| برکر از دسترس خارج (هر حالت صف) | connection refused | ورکرها به‌صورت نمایی عقب می‌نشینند (1 ثانیه → 60 ثانیه)، دوباره وصل می‌شوند و ادامه می‌دهند؛ fetcher تا موفقیت pushها آفست را نگه می‌دارد |

## منابع محدود

- **صف‌ها محدودند** (`QUEUE_MAX_SIZE`، `RETRY_MAX_SIZE`): وقتی پر شوند، pushها رد و لاگ می‌شوند — یک قطعی نمی‌تواند بی‌صدا دیسک شما را پر کند.
- **حافظه محدود است**: ورکر polling هر `POLLING_RESTART_INTERVAL` بسته خودش را ری‌استارت می‌کند (قابل پیکربندی؛ مقدار `0` غیرفعالش می‌کند).
- **لاگ‌ها در برابر path traversal امن‌اند**: `LOG_DIR`/`LOG_FILE` نمی‌توانند به بیرون از پروژه اشاره کنند.

## رده‌بندی خطاها در صف retry

`RetryableException::isRetryable()` خطاها را دسته‌بندی می‌کند تا فقط خرابی‌های *گذرا* دوباره تلاش شوند:

- HTTP با کد `429 Too Many Requests` (با رعایت `parameters.retry_after` تلگرام وقتی موجود باشد)
- HTTP با کد `5xx` / «خطای سرور»
- timeoutها (`timeout`، `timed out`، `connect`)
- `cURL error N`
- هر زیرکلاس از `RetryableException` که خودتان پرتاب کنید

هر چیز دیگری (400 با پیام «chat not found»، 403 با پیام «bot blocked» و ...) دائمی است — لاگ می‌شود، دوباره تلاش نمی‌شود.

## تست وضعیت قابلیت اطمینان خودتان

مجموعهٔ تستی که همراه فریمورک می‌آید شامل اجزای مرتبط با کرش است (اتمیک‌بودن ذخیرهٔ آفست، درایورهای صف، چرخهٔ retry، مسیرهای اعتبارسنجی dispatcher وبهوک):

```bash
php tests/run.php --filter=Queue     # queue driver behaviour
php tests/run.php --filter=Offset    # offset storage
php tests/run.php --filter=Retry     # retry lifecycle
php tests/run.php --filter=Webhook   # webhook validation layers
```

برای اطمینان سرتاسری، همان رویکرد تست یکپارچگی را روی دیپلوی خودتان تکرار کنید: وبهوک را ثبت کنید، یک پیام نشانه بفرستید، ورکر را در میانهٔ کار با `kill -9` بکشید و تحویل دوباره را در `getWebhookInfo` / لاگ‌ها بررسی کنید.
