# وبهوک — دریافت آپدیت‌ها از تلگرام

## راه‌اندازی

```dotenv
# .env
BOT_MODE="webhook_direct"          # or webhook_queue
BOT_WEBHOOK_URL="https://yourdomain.com/webhook.php"
BOT_WEBHOOK_SECRET="a-long-random-string"   # openssl rand -hex 32
WEBHOOK_CHECK_IP=true
```

یک بار ثبت کنید (تلگرام HTTPS با گواهی معتبر الزام می‌کند):

```bash
curl "https://api.telegram.org/bot<TOKEN>/setWebhook?url=https://yourdomain.com/webhook.php&secret_token=<SECRET>"
curl "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"   # verify: pending_update_count=0, no last_error
```

لغو ثبت (وقتی برمی‌گردید به polling — این کار را *قبل از* اجرای `bot.php` انجام دهید، چون دو منبع آپدیت بر سر همان جریان می‌جنگند):

```bash
curl "https://api.telegram.org/bot<TOKEN>/deleteWebhook"
```

## پنج لایهٔ اعتبارسنجی

هر درخواستی که به `webhook.php` می‌رسد، به این ترتیب از `WebhookDispatcher` عبور می‌کند:

1. **حجم بدنه** — بیشتر از 1 مگابایت → `413`. (تلگرام هرگز payload بزرگ‌تری نمی‌فرستد؛ هر چیز بزرگ‌تر، تلگرام نیست.)
2. **ویت‌لیست IP** — با `WEBHOOK_CHECK_IP=true`، درخواست‌هایی که IPشان خارج از ساب‌نت‌های رسمی تلگرام است → `403`. بازه‌ها همان‌هایی هستند که در مستندات تلگرام منتشر شده‌اند (`149.154.160.0/20`، `91.108.4.0/22`، `91.108.8.0/22`، `91.108.56.0/22`، `91.108.16.0/22`، `95.161.64.0/20`).
3. **توکن مخفی** — با تنظیم `BOT_WEBHOOK_SECRET`، هدر `X-Telegram-Bot-Api-Secret-Token` باید مطابقت داشته باشد؛ مقایسه با `hash_equals()` انجام می‌شود (امن در برابر حملات زمانی). عدم تطابق → `403`.
4. **اعتبارسنجی JSON** — بدنه باید به یک شیء حاوی `update_id` تجزیه شود. در غیر این صورت → `400`.
5. **مسیریابی** — `webhook_direct` پلاگین‌ها را به‌صورت همگام اجرا می‌کند و فقط اگر چیزی استثنا پرتاب نکرده باشد `200` جواب می‌دهد؛ `webhook_queue` آپدیت را در صف قرار می‌دهد و بلافاصله `200` جواب می‌دهد.

رد‌شدن اعتبارسنجی هرگز آپدیت را به شکلی از بین نمی‌برد که قابل بازیابی نباشد — تلگرام آپدیت‌هایی را که برایشان `2xx` نگرفته دوباره می‌فرستد.

## پشت Cloudflare / پروکسی‌های nginx (مهم)

اگر درخواست‌های تلگرام از طریق Cloudflare (یا هر reverse proxy دیگری) به PHP برسند، `REMOTE_ADDR` در PHP یعنی IP *پروکسی* است، نه تلگرام — و بررسی IP تک‌تک درخواست‌ها را رد می‌کند. دو راهکار عملی:

- **پروکسی جلوی سرور:** `WEBHOOK_CHECK_IP=false` را نگه دارید و برای احراز هویت ورودی‌ها به **توکن مخفی** تکیه کنید (آن را بلند بسازید — ۳۲ کاراکتر هگز یا بیشتر). فریمورک در تست پروداکشن دقیقاً همین‌طور اعتبارسنجی شده است.
- **پروکسی IP واقعی را رد می‌کند:** پروکسی را طوری پیکربندی کنید که `X-Forwarded-For` / `X-Real-IP` را بفرستد *و* PHP به آن اعتماد کند — در این صورت `WEBHOOK_CHECK_IP=true` کار می‌کند. این کار را فقط وقتی انجام دهید که پروکسی تحت کنترل شما باشد؛ در غیر این صورت این هدر قابل جعل است.

قاعدهٔ سرانگشتی: **بررسی IP = دسترسی مستقیم؛ توکن مخفی = دسترسی از پشت پروکسی.** استفاده از هر دو هم اشکالی ندارد.

## رفتار حالت‌ها روی نقطهٔ ورود وبهوک

| `BOT_MODE` | کارِ `webhook.php` |
|------------|--------------------------|
| `webhook_direct` | اعتبارسنجی → `Processor::handle()` → `200` بعد از اتمام |
| `webhook_queue` | اعتبارسنجی → افزودن به صف → بلافاصله `200` |
| `update_direct` | اعتبارسنجی → `Processor::handle()` → `200` (کار می‌کند اما هشداری لاگ می‌شود — به‌صورت صریح `webhook_direct` را ترجیح دهید) |
| `update_queue`، `cronjob_*` | `500` + پیام توضیحی — این حالت‌ها فقط CLI هستند |

ردیف آخر همان نگهبان SAPI نسخهٔ v2.4.0 است ([bot-modes.md](bot-modes.md)): حالت CLI روی نقطهٔ ورود وب دیگر نمی‌تواند داخل ورکر PHP-FPM شما حلقهٔ بی‌نهایت راه بیندازد (کاری که قبلاً به `Read timeout expired` در سمت تلگرام و یک 502 از وب‌سرور شما ختم می‌شد).

## معناشناسی پاسخ — چرا 200 مهم است

تلگرام هر تحویل وبهوکی را که `2xx` نگیرد، با backoff و تا چندین ساعت، دوباره تلاش می‌کند. فریمورک از این واقعیت به‌صورت صادقانه استفاده می‌کند:

- `200` **فقط بعد از** آن فرستاده می‌شود که آپدیت پردازش شده (حالت direct) یا با خیال راحت در صف قرار گرفته باشد (حالت queue).
- یک استثنا حین پردازش → `500` → تلگرام بعداً دوباره تحویل می‌دهد → آپدیت **از دست نمی‌رود**، اما اگر تلاش اول واقعاً قبل از کرش کامل شده باشد، *دو بار پردازش خواهد شد*. این دقیقاً تعریف تحویل at-least-once است — برای idempotent‌کردن هندلرها به [reliability.md](reliability.md) نگاهی بیندازید.
- ورکری که چند دقیقه طول می‌کشد تا جواب بدهد یک باگ است، نه یک ویژگی: timeout کلاینت تلگرام حدود 60 ثانیه است. کارهای کند را به `webhook_queue` منتقل کنید.

## ثبت وبهوک با allowed updates (اختیاری)

چیزی که تلگرام برایتان می‌فرستد را به انواع آپدیتی محدود کنید که پلاگین‌هایتان واقعاً هندل می‌کنند:

```bash
curl "https://api.telegram.org/bot<TOKEN>/setWebhook?url=...&secret_token=...&allowed_updates=[\"message\",\"edited_message\",\"callback_query\",\"channel_post\",\"edited_channel_post\"]"
```

## بررسی سلامت

`getWebhookInfo` داشبورد شماست — این‌ها را زیر نظر داشته باشید:

- `pending_update_count` — آپدیت‌هایی که چون endpoint شما خراب/کند است در تلگرام صف شده‌اند. رشد مداوم = یک رخداد (incident).
- `last_error_message` / `last_error_date` — دقیقاً همان خرابی تحویل (timeoutها، خطاهای TLS، توکن مخفی اشتباه).

چک‌لیست دیپلوی برای حالت وبهوک:

1. `webhook.php` از طریق HTTPS در دسترس باشد (با مرورگر تست کنید: یک GET خالی باید `400 empty` بدهد — این پاسخ خود dispatcher است).
2. `BOT_WEBHOOK_SECRET` دست‌کم ۳۲ کاراکتر تصادفی و در `.env` و `setWebhook` یکسان باشد.
3. `WEBHOOK_CHECK_IP` با توپولوژی شبکهٔ شما مطابق باشد (بخش پروکسی را ببینید).
4. بعد از یک پیام تستی، `getWebhookInfo` تمیز باشد و اثر جانبی پلاگین شما قابل مشاهده باشد.
