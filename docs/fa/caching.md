# کش — CacheManager

یک API استاتیک واحد روی چهار درایورِ قابل تعویض، که تماماً از طریق `.env` پیکربندی می‌شود. سشن‌ها، ترجمه‌ها، تعاریف دکمه‌ها و (به‌صورت اختیاری) کشف پلاگین‌ها همگی روی این لایه سوارند — تعویض درایور، داستان ماندگاری کل فریمورک را بدون دست زدن به کد تغییر می‌دهد.

```php
use alirezax5\TelegramBase\App\Cache\CacheManager;
```

> هر ادعایی در این سند به‌صورت زنده تأیید شده است (2026-10-11) روی بک‌اندهای واقعی در یک سرور پروداکشن: مجموعهٔ ۱۷-بررسی روی `array`، `file`، `memcached` (PHP 8.5) و `redis` سبز بود، به‌علاوهٔ یک ماتریس ۹-نقطه‌ای ماندگاری بین‌پروسه‌ای برای هر درایور پایدار. بخش *تأیید زنده* را در انتهای صفحه ببینید و همچنین [CHANGELOG](../../CHANGELOG.md).

## درایورها

| `CACHE_DRIVER` | بک‌اند | بین‌پروسه‌ای | تگ‌ها | نکات |
|---|---|---|---|---|
| `array` (پیش‌فرض) | حافظهٔ هر پروسه | ✗ | ✗ | بدون نیاز به پیکربندی؛ وضعیت دقیقاً به اندازهٔ عمر پروسه زندگی می‌کند |
| `file` | دیسک، `CACHE_PATH` | ✓ | ✗ | بدون سرویس اضافه؛ دایرکتوری‌های دوسطحی هش‌شده؛ payloadهای PHP-serialized |
| `redis` | افزونهٔ phpredis (`redis.so`) | ✓ | ✗ | payloadهای JSON؛ برای دیپلوی‌های چند-پروسه‌ای توصیه می‌شود |
| `memcached` | افزونهٔ `memcached` + سرور | ✓ | ✗ | payloadهای JSON؛ ذاتاً فرّار (volatile) |

**زنجیرهٔ fallback (تأییدشده):** اگر درایور درخواستی در دسترس نباشد — افزونه غایب، سرور غیرقابل‌دسترس، احراز هویت ناموفق، مسیر غیرقابل‌نوشتن — فریمورک یک هشدار لاگ می‌کند و به‌جای شکستن بوت، **به `array` برمی‌گردد**. درخواست `memcached` روی PHPیی بدون این افزونه دقیقاً همین نتیجه را داد: `driver=array` و بقیه چیزها بدون تغییر. با `CacheManager::getDriver()` بررسی کنید واقعاً چه چیزی گرفته‌اید.

> ⚠️ درایور `array` محدود به همان پروسه است. یک دیمون polling *یک* پروسهٔ بلندعمر است، پس `array` آنجا «کار می‌کند»؛ اما وبهوک (ورکرهای FPM به‌ازای هر درخواست) و ورکرهای صف (یک پروسه به ازای هر ورکر) هرگز وضعیت را به اشتراک نمی‌گذارند. اگر سشن‌ها، شمارنده‌ها یا `remember()` باید بین پیام‌ها/پروسه‌ها باقی بمانند، از `file`، `redis` یا `memcached` استفاده کنید. این موضوع به‌صورت زنده نشان داده شد: مقادیری که در پروسهٔ A نوشته شد و در پروسهٔ B خوانده شد — روی هر سه پایدار می‌ماند و روی `array` نتیجه `<MISS>` است (عمداً).

## پیکربندی (.env)

```dotenv
CACHE_DRIVER=file            # array | file | redis | memcached
CACHE_PREFIX=tgbase_         # key namespace (also the flush() safety boundary)
CACHE_TTL=3600               # default TTL seconds when put() has no explicit ttl
CACHE_PATH=/tmp/tgbase-cache # file driver only
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
REDIS_PASSWORD=              # required if the server has requirepass (NOAUTH otherwise)
REDIS_DATABASE=0
MEMCACHED_HOST=127.0.0.1
MEMCACHED_PORT=11211
```

## API

| متد | رفتار |
|---|---|
| `get($key, $default = null)` | مقدار یا مقدار پیش‌فرض در صورت نبود/انقضا |
| `put($key, $value, ?int $ttl = null)` | ذخیره؛ ttl برابر `null` → `CACHE_TTL` |
| `remember($key, callable $cb, ?int $ttl = null)` | مقدار کش‌شده را برمی‌گرداند یا `$cb` را اجرا و نتیجه را کش می‌کند |
| `has($key)` | وجود دارد و منقضی نشده |
| `forget($key)` | حذف یک کلید |
| `flush()` | حذف **همهٔ کلیدهای namespace این فریمورک** — به نکات هر درایور نگاه کنید |
| `increment($key, $by = 1)` / `decrement($key, $by = 1)` | شمارنده‌ها |
| `getDriver()` / `isInitialized()` / `tagsSupported()` | دریافت اطلاعات داخلی |
| `putWithTags()` / `getWithTags()` / `rememberWithTags()` / `flushTags()` | API سبک تگ‌دار که روی هر درایوری کار می‌کند (fallback مبتنی بر پیشوند) |
| `tags([...])` | کش تگ‌دار بومی — مگر اینکه درایور از تگ پشتیبانی کند **استثنا پرتاب می‌کند** (هیچ‌کدام از چهار درایور پشتیبانی نمی‌کنند) |

### معناشناسی TTL (تأییدشده با انتظارهای واقعی)

`put('k', 'x', 2)` → `has` درست → بعد از 3 ثانیه → `has` نادرست، `get` مقدار پیش‌فرض را برمی‌گرداند. TTLهای بک‌اند دقیقاً با پیکربندی می‌خوانند: یک ورودی 300 ثانیه‌ای زیر `redis-cli` مقدار `ttl=297s` نشان داد، یک سشن 3600 ثانیه‌ای `ttl=3597s`، و یک کش ترجمهٔ 60 ثانیه‌ای `ttl=57s`. ورودی‌های منقضی در `file`/`redis` به‌صورت تنبل حذف می‌شوند (هنگام دسترسی) یا توسط بک‌اند (`setex` در `redis`).

### فرمت‌های ذخیره‌سازی

- **redis** — `setex` با `json_encode(JSON_UNESCAPED_UNICODE)`. payloadها باید از گذر رفت‌وبرگشت JSON سالم بیرون بیایند: اسکالرها و آرایه‌ها بله؛ اشیای PHP به شکل آرایه برمی‌گردند؛ resource مجاز نیست.
- **memcached** — JSON از طریق همان خانوادهٔ متدهای ذخیره؛ مقادیر به‌صورت شفاف توسط افزونه (un)serialize می‌شوند.
- **file** — payloadهای PHP `serialize()`، ابتدا مُهر انقضا، زیر `CACHE_PATH/ab/cd/<sha1>`.
- **array** — متغیرهای سادهٔ PHP؛ هیچ چیزی به دیسک یا شبکه دست نمی‌زند.

### چیدمان کلید (نمای خام بک‌اند)

| درایور | کلید خام برای `put('lang:fa', …)` با `CACHE_PREFIX=tgbase_` |
|---|---|
| redis | `tgbase_lang:fa` |
| memcached | `tgbase_:lang:fa` (Illuminate یک `:` به پیشوند اضافه می‌کند) |
| file | `CACHE_PATH/<h1>/<h2>/<sha1>` |

### شمارنده‌ها — یک نکتهٔ ظریف (تأییدشده)

`increment()` روی کلیدِ **ناموجود**: `array`/`file`/`redis` آن را می‌سازند (`incBy`)، ولی `memcached` مقدار `false` برمی‌گرداند (Illuminate مقدار اولیه‌ای نمی‌فرستد). الگوی قابل‌حمل: اول مقدار بذر بگذارید — `CacheManager::put($k, 0, $ttl); CacheManager::increment($k);`

### flush() — دامنهٔ هر درایور

- `array` — فقط همین پروسه.
- `file` — هر چیزی داخل `CACHE_PATH` (دایرکتوری اختصاصی؛ امن).
- `redis` — **محدود به پیشوند**: با `SCAN` روی `{CACHE_PREFIX}*` حرکت می‌کند و فقط همان کلیدها را `UNLINK` می‌کند. روی نمونه‌های اشتراکی امن است (تأییدشده روی Redis مشترک با کش شیءگرای WordPress — سایر کلیدها دست‌نخورده ماندند). با پیشوند خالی از اجرا امتناع می‌کند.
- `memcached` — ⚠️ `MemcachedStore::flush()` یک `flush_all` در سطح سرور صادر می‌کند. روی memcached **اشتراکی** این کار کش بقیهٔ اپلیکیشن‌ها را نابود می‌کند — آنجا از آن صرف‌نظر کنید (مجموعهٔ تست عمداً همین کار را می‌کند).

## چه چیزهایی روی کش سوارند

| مصرف‌کننده | کلید | کلید تنظیم TTL |
|---|---|---|
| [سشن‌ها](sessions.md) | `tgbase:session:{chatId}` | `SESSION_TTL` (پیش‌فرض 3600، حداقل 60) |

| [تعاریف دکمه‌ها](buttons.md) | `buttons:all` | `BUTTONS_CACHE_TTL` (پیش‌فرض 300)، کلید خاموش‌کنندهٔ `BUTTONS_CACHE_ENABLED` |
| کشف پلاگین | (داخلی) | `PLUGIN_CACHE_ENABLED` + `PLUGIN_CACHE_TTL` |

## تأیید زنده (P-CACHE، 2026-10-11)

| مجموعه | نتیجه |
|---|---|
| مجموعهٔ درون-پروسه‌ای ۱۷-بررسی × `array` / `file` / `memcached` (PHP 8.5) / `redis` | روی همهٔ آن‌ها **PASS** |
| درخواست memcached روی PHP 8.4 (بدون افزونه) → بازگشت graceful به `array` | **PASS** (زنجیرهٔ مستندشده) |
| ماتریس بین‌پروسه‌ای (`set` در یک پروسه → `get` در پروسهٔ دیگر): اسکالر، آرایهٔ تودرتو، شمارندهٔ 5→6، بازگشتِ *عدد تصادفی کاشته‌شده* در `remember`، پیوستگی شناسه و payload سشن، payload بر `lang:fa`، payload بر `buttons:all` | روی `file`، `redis`، `memcached` **9/9 PASS**؛ روی `array` دقیقاً مثل مستندات miss می‌شود |
| بازرسی بک‌اند | کلیدهای redis با شمارش معکوس TTL زنده؛ کلیدهای خام memcached زیر `tgbase_:`؛ فایل‌استور با مُهرهای انقضای قابل مشاهده |
| پایپ‌لاین واقعی: `/cache demo hello` (توزیع 1) → `/cache demo` (توزیع 2، پروسهٔ تازه) → `demo = hello`؛ `/session-set`/`/session-get` همین‌طور | **PASS** |

یک نقص واقعی در همین تمرین پیدا و رفع شد: **`CacheRedisStore::flush()` حلقهٔ SCAN خود را روی اولین صفحهٔ خالی MATCH خاتمه می‌داد** (رایج در keyspaceهای بزرگ/اشتراکی) — هیچ چیزی حذف نمی‌کرد در حالی که `true` برمی‌گرداند (P-CACHE-F001 در CHANGELOG).
